先说结论

这篇文章不讨论“理论上能不能跑”，而是记录一套已经在 4 张 H800 上验证过的部署方案：使用 ModelScope 的 DeepSeek-V4-Flash-0731 权重，SGLang v0.5.16，上下文限制为 64K，MoE 后端选择 Marlin，并启用 EAGLE 推测解码。它的目标是稳定、经济、实用，而不是盲目追求 1M 上下文或实验室峰值吞吐。

本文的权重和推测解码要分清：部署对象是 DeepSeek-V4-Flash-0731；本文实测使用的是 EAGLE 参数，不启用 DSpark 推测解码。两条路径的启动参数与验证条件不能混写，具体要以实际权重和 SGLang 版本为准。

01｜为什么要升级到 0731？

先看版本背景：0731 是 DeepSeek 发布的 DeepSeek-V4-Flash 正式开源版本，官方模型卡明确说明它取代了此前的 Flash Preview，并重点增强 Agent 能力。对部署者来说，这次升级不是简单换一个目录名，而是从预览权重切换到正式版本。官方模型卡同时给出了 DSpark 推测解码路径；本文为了对应已经在 H800 4 卡上验证成功的脚本，仍采用 EAGLE，二者不在同一条启动命令里混用。

如果只是普通问答，旧版 V4-Flash Preview 可能已经够用。但当模型被放进代码助手、自动化流程或企业 Agent 里，真正决定体验的往往不是“会不会聊天”，而是能不能稳定地拆任务、调用工具、修改代码，并把复杂任务做完。

DeepSeek 官方把 0731 定义为 V4-Flash 的正式新版本，重点增强了 Agent、代码和工具使用能力。换句话说，这次升级的理由不是模型名字变了，而是它更适合作为一个“干活的模型”。

升级判断：0731 不只是超过上一代 Preview，在官方公开的多项 Agent / Coding 测试中也超过了 V4-Pro Preview；普通聊天看不出全部差距，代码修改、工具调用、自动化执行和复杂 Agent 任务，才是它价值最集中的地方。

02｜硬件和部署目标：不是追求最大，而是追求可用

本次部署环境是 4 张 H800，采用 TP4。上下文长度没有追求官方宣传的极限，而是设置为 64K。这是一个很现实的工程取舍：上下文越长，KV Cache 和调度压力越大，实际并发能力也越容易下降。

如果业务主要是代码问答、工具调用、企业知识查询和中等长度文档处理，64K 已经能覆盖大量场景。先把稳定服务跑起来，再根据真实流量决定是否扩上下文，比一开始就把显存全部押在 1M 上更稳妥。

为什么是 64K：它不是理论上限，而是经济平衡点

模型权重是相对固定的成本，KV Cache 则会随着请求长度和并发数增长。其他条件相同时，128K 的单请求缓存压力大致是 64K 的两倍，256K 大致是四倍；DeepSeek-V4 的压缩注意力会改变精确比例，但不会改变这个方向。

上下文窗口 相对 64K 的缓存压力 适合的判断
64K 1 倍 代码 Agent、工具调用、日常长对话
128K 约 2 倍 单任务更长，但并发余量下降
256K 约 4 倍 需要明确的长上下文业务
1M 约 16 倍 专门的长上下文集群与缓存方案

对 Code Agent 来说，关键不是把整个仓库一次性塞进上下文。更合理的路径是先感知目录和语言结构，再检索、筛选最相关的文件，执行修改后根据测试结果继续迭代。64K 足够覆盖系统提示词、任务描述、关键源码、工具输出和多轮历史，同时为 Marlin、EAGLE、CUDA Graph、NCCL 和 KV Cache 留出余量。

sudo modprobe nvidia-peermem sudo docker run --gpus all \ --network host \ --name DeepSeek-V4-Flash \ --shm-size=32g --ipc=host -d \ --privileged \ -v /modelshare_readonly/deepseek-ai/DeepSeek-V4-Flash-0731/:/deepseek-ai/DeepSeek-V4-Flash/ \ -v /dev/infiniband:/dev/infiniband \ -e CUDA_VISIBLE_DEVICES=0,1,2,3 \ -e NCCL_IB_HCA="mlx5_0:1,mlx5_2:1,mlx5_3:1,mlx5_5:1" \ -e GLOO_SOCKET_IFNAME=bond0 \ -e NCCL_SOCKET_IFNAME=bond0 \ -e NCCL_DEBUG=INFO \ lmsysorg/sglang:v0.5.16 \ python3 -m sglang.launch_server \ --trust-remote-code \ --model-path /deepseek-ai/DeepSeek-V4-Flash \ --tp 4 \ --served-model-name DeepSeek-V4-Flash \ --tool-call-parser deepseekv4 \ --reasoning-parser deepseek-v4 \ --context-length 65536 \ --host 0.0.0.0 --port 40000 \ --moe-runner-backend marlin \ --speculative-algorithm EAGLE \ --speculative-num-steps 3 \ --speculative-eagle-topk 1 \ --speculative-num-draft-tokens 4 \ --mem-fraction-static 0.88

这条命令里最容易看错的三件事

第一，容器内路径不是版本名。宿主机挂载的是 0731 目录，但容器内统一映射成 /deepseek-ai/DeepSeek-V4-Flash，这是路径别名，不代表回退到了旧版模型。

第二，API 模型名由 served-model-name 决定。客户端请求中应填写 DeepSeek-V4-Flash，而不是随意填写宿主机目录名。

第三，本文使用 EAGLE，不是 DSpark。这两条推测解码路径的权重与参数不能混写；部署时必须以实际模型权重和 SGLang 版本为准。

04｜为什么选择 Marlin，而不是看起来更快的后端

MoE 后端的第一关不是峰值算力，而是显存预算。模型权重只是显存的一部分，运行时还要为 MoE workspace、KV Cache、CUDA Graph、NCCL 通信以及 EAGLE 的草稿和验证过程预留空间。

Marlin 走的是 Hopper 上更适合原始 FP4 专家权重的 W4A16 路径：权重保持低比特存储，计算时融合反量化和矩阵乘法，避免把大量专家权重完整展开成更高精度格式。它未必在所有负载下都是最快的，但更容易把模型、KV Cache 和推测解码同时放进 H800 4 卡。

相反，DeepGEMM、FlashInfer、CUTLASS 等路径通常面向特定 FP8、MXFP4 或更新的融合 kernel。它们可能有更高的理论性能，但也可能在初始化时申请更大的 workspace，或者要求不同的 checkpoint 格式。对当前这套显存预算来说，“启动不了”比“理论上更快”更需要优先解决。

常见 MoE Runner 横向比较

后端 主要定位 H800 4 卡本方案的影响
marlin Hopper W4A16 / FP4 MoE 显存友好；适配当前原始 0731 权重，本文实测可启动
auto 自动选择可用后端 不保证选到显存最省的路径；版本升级后选择结果也可能变化
deep_gemm 高性能 FP8 / GEMM 路径 更依赖 FP8 权重和运行时 workspace；当前组合切换后显存压力更大
triton / triton_kernel 通用或 SGLang Triton fallback 兼容性较宽，但专用 FP4 优化和显存效率通常不如 Marlin
flashinfer_mxfp4 FlashInfer MXFP4 MoE 依赖 checkpoint、FlashInfer 版本和架构；不应与当前可启动方案直接等价
flashinfer_trtllm FlashInfer / TRT-LLM 融合 MoE 高性能取向，但可能预分配更大的 workspace，容易挤压 KV 和 EAGLE 余量
flashinfer_trtllm_routed 带 routed MoE 的 TRT-LLM 路径 更依赖特定量化格式和路由实现；不是当前权重的首选验证路径
flashinfer_cutlass / cutlass CUTLASS 融合矩阵乘路径 适合部分 FP4 / NVFP4 或更新硬件路径；格式和 workspace 约束更明显
flashinfer_cutedsl CuteDSL MoE kernel 版本、架构和量化路径耦合较强，需单独做端到端验证
aiter / humming 其他平台或实验性实现 不作为 H800 4 卡这套稳定生产基线

注意：SGLang 的“可选后端”列表不等于“当前模型、当前权重、当前 GPU 都适用”。最终判断必须以权重格式、SGLang 版本和本机端到端启动结果为准。

工程判断：如果更换后端后 OOM，不能只看 nvidia-smi 还有多少空闲显存。失败点可能发生在权重重排、MoE workspace 预分配、CUDA Graph 捕获或 EAGLE 初始化阶段。

后端选择的实际优先级

第一优先：权重格式匹配；第二优先：能否在显存预算内完成初始化；第三优先：稳定性；最后才是峰值 tokens/s。你的 Marlin 方案正是按照这个顺序做出的选择。

05｜启动后要验证什么

服务启动成功只是第一关。建议按下面顺序验证，避免把“进程活着”误认为“模型可用”。

① 普通对话：确认模型名、中文输出和流式响应。

② 思考模式：确认 reasoning_content 与最终答案能正确分离。

③ 工具调用：确认 tool_calls 的函数名和参数 JSON 正常。

④ 长上下文：从 8K、32K 逐步增加到 64K，不要一上来用极限请求压垮 KV Cache。

⑤ 性能记录：至少记录首 token 延迟、输出速度、并发数、显存占用和 EAGLE 接受情况。

建议的 API 最小验证

curl http://127.0.0.1:40000/v1/chat/completions \ -H "Content-Type: application/json" \ -d '{"model":"DeepSeek-V4-Flash","messages":[{"role":"user","content":"请用三句话介绍你自己。"}]}'

高阶验证：用 EvalScope 评测在线 API

最小 curl 只能证明“接口能返回”，不能说明模型在数学、知识和指令遵循上的整体表现。可以在独立的评测环境安装 EvalScope，通过 OpenAI 兼容接口评测当前已经启动的服务：

pip install evalscope

evalscope eval \
  --model DeepSeek-V4-Flash \
  --api-url http://127.0.0.1:40000/v1 \
  --api-key EMPTY \
  --eval-type openai_api \
  --datasets gsm8k arc ifeval \
  --limit 20 \
  --generation-config '{"temperature":0.6,"max_tokens":2048}'

怎么读结果：gsm8k 看数学推理，arc 看基础知识，ifeval 看指令遵循。命令中的 --limit 20 是先跑小样本确认评测链路；正式对比时去掉它，或者固定同一批数据、采样参数和重复次数。

注意：EvalScope 评测的是服务 API 的输出结果，不等同于 H800 的吞吐压测。吞吐、首 token 延迟、并发和显存仍应单独记录；如果评测环境不在推理机上，把 127.0.0.1 换成推理机地址，并确认 40000 端口可访问。

06｜最后总结：这次升级值得吗？

如果你的场景只是普通闲聊，0731 的升级收益未必值得立刻更换全部基础设施；但如果你要做代码 Agent、工具调用、自动化执行或复杂任务编排，0731 的升级方向就非常明确。

在硬件侧，H800 4 卡并不适合无限堆上下文和所有高性能后端。本文这套 64K + Marlin + EAGLE 的组合，牺牲了一部分极限能力，换来更现实的显存余量和服务稳定性。

模型升级解决“能力够不够”的问题；Marlin、64K 上下文和显存预算，解决“服务能不能长期跑”的问题。

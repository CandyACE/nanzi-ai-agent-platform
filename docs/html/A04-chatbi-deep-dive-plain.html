深入 ChatBI：问数是护栏工程

端到端流程 · 分诊 · Binding · 门禁 · 计划自愈 · 结果栈 · 门户

项目声明

本项目为个人开源，供自由学习交流，遵循 MIT 开源协议。

仓库：RandyChen1985/nanzi-ai-agent-platform

上篇讲了怎么建好一个 ChatBI 专家；这篇讲它跑起来之后内部怎么干活。很多人以为问数 =「让大模型写一条 SQL」——那是演示。NanZi 的 ChatBI 是：先分诊这轮要不要查库 → 再理解意图 → 取 Schema → 绑表绑列 → 过一串门禁 → 才执行 → 结果进栈 → 可下钻、做简报、订黄金报表。

每章开头仍用大白话交代「这节解决什么」，再展开技术细节。读完后你应该能：

· 先有一张端到端流程图（第 00 节），再往下拆分诊、门禁、结果栈

· 在 Trace 里认出分诊类型，知道「为什么没生成 SQL」其实是正常的

· 看到 [SCHEMA_GATE] / [SQL_STATIC_GATE] 知道卡在哪、怎么修

· 理解 Binding、计划卡片、结果栈、门户与简报各自干什么

· 按排障顺序定位：分诊 → 门禁前缀 → Binding → 修复轮次 → 元数据/授权

先给结论：ChatBI 的护栏强度是三类专家里最强的。外层路由只负责「把话交给问数专家」；本轮要不要写 SQL、写之前过几道闸，全由 ChatBI 内部说了算。口径与元数据质量决定上限——模型再强，表结构脏、授权乱，护栏也只能拦错，不能替你补治理。

00｜端到端主流程：用户一句话之后发生了什么

大白话：先别钻分诊枚举和门禁前缀。这一节只回答一件事：用户敲下「上个月华东销售额」之后，平台按什么顺序干活。后面各章是这条流水线上的放大镜；迷路时随时回到这里对号入座。

下面以新查数（new_data_query）主路径为准；复用结果、改格式、写简报等会在分诊后短路，跳过 Schema/SQL。外层 Router / 会话亲和性负责「是否交给 ChatBI」，真正流水线从分诊开始。

新查数主路径（示意）

① 用户输入 → ② 分诊 → ③ 结构化需求分析（IntentFrame）
→ ④ 查样例集（Few-Shot） → ⑤ 获取数据集 Schema
→ ⑥ 构建 SQL（+ sql_plan） → ⑦ 各类门禁 + Binding 预检
→ ⑧ 执行查询 → ⑨ 结果检查 / 修复轮 → ⑩ 输出 · 入栈 · 交付

步骤 做什么 要点 / Trace 里看什么
① 用户输入 对话 / Embed / V1 进入 ChatBI 外层已选中 DataQuery；亲和性 KEEP/BREAK/UNCERTAIN 决定是否留在问数会话
② 分诊 判定本轮类型 DataQueryTurnClassifier 为最终判定。非查数走处置/委派；复用/呈现可跳过后续查库（详第 02 节）
③ 结构化需求分析 生成 IntentFrame 指标 / 维度 / 筛选语义 / 时间 / 粒度 → 派生 Schema 检索词。Trace「用户需求分析」卡片（详第 03 节）
④ 查样例集 Few-Shot 案例检索 相似历史问法与 SQL 作参考；未命中也要可观测，避免模型从零瞎编口径
⑤ 获取数据集 get_dataset_schema 仅授权元数据范围内。无授权 / 服务不可用 / 未同步 / 连续 miss → 终止。多候选接近 → 先澄清
⑥ 构建 SQL ReAct 生成只读 SQL 可附带 sql_plan 前端卡片（goal/tables/metrics/…）。须先 Schema 后 SQL，顺序反了会被 SCHEMA_GATE 打回
⑦ 各类门禁 工具返回前缀，不真执行 SCHEMA / STATIC / REPEAT / FAILED_REPEAT / PLAN / TIME_RANGE / Performance…（详第 04 节）。Binding 把表↔数据集钉死
⑧ 执行查询 execute_sql_query 预检通过后落库只读查询；跨 dataset 表引用可自动升级联邦（详第 07 节）
⑨ 结果检查 空结果 / 报错 / 异常指标 空结果结合 IntentFrame 诊断筛选项；报错进 repair；比率/时延异常触发复核。成功则推入结果栈（深度≤10）
⑩ 输出与交付 回答 / 图表 / 简报 自然语言呈现；追问下钻走结果栈；简报与订阅须绑 result_id（详第 06 节）。可选 Grounding 事实审核

三条旁路（不必走完全程）

· 复用 / 分析 / 改格式：分诊后直接 synthesis，用结果栈里已有数据

· 元数据问答：问有哪些表字段，未必执行业务 SQL

· 非查数：本地帮助、结果动作、或 handoff 委派主助手 / 联网助手

排障怎么用这张图：Trace 停在哪一步，就翻对应章节——分诊不对 → 02；IntentFrame / Schema → 03；门禁前缀 / Binding → 04；计划与修复 → 05；栈与门户 → 06。别一上来改 system prompt。

01｜定位：薄 Runner + 厚护栏

大白话：可以把 ChatBI 想成「带安检的数据分析师」：用户每说一句话，先判断是查数、追问、看表结构、还是闲聊委派；真要查库，必须先摸清有哪些表、再写只读 SQL，写完还要过安检才执行。底层仍是 AgentScope 的「想一步、用工具、再想」循环，外面多了一整层 NanZi 自己写的安检与记忆。

代码形态：薄门面 DataAgentRunner + 厚域逻辑 app/services/ai/runners/chatbi/（分诊处置、Schema 预取、工具门禁包装、计划、修复、联邦升级、合成流等）。外层 Executor 是 DataQueryExecutor；ReAct 循环仍是 AgentScope reply_stream。

和代码怎么对应

· 第 00 节流水线 = 产品视角；本节说代码落点

· 门面 DataAgentRunner 编排；域逻辑在 runners/chatbi/

· ReAct 主循环与修复轮：native_turn / react_stream；状态在 DataRunState

02｜分诊：本轮到底要不要写 SQL

大白话：用户连着聊「上个月销售额」「换成柱状图」「这个表有哪些字段」「帮我写个邮件」——不能句句冲进数据库。分诊就像急诊分诊台：有的要开刀（新查数），有的只看片子（分析已有结果），有的转科（委派通用助手）。Trace 里先看分诊类型，再骂「怎么没 SQL」。

类型 白话 通常路径
new_data_query 新开一刀查数 意图帧 → Schema → SQL
data_followup_query 在上一刀上改条件/下钻 继承结果栈上下文再查
federated_data_query 跨多个数据集 联邦升级 + Binding 校正
metadata_query 问有哪些表/字段 元数据问答，未必执行业务 SQL
reuse_previous_result 直接用上次数 可跳过 Agent，走 synthesis
result_analysis / result_presentation / format_correction 分析 / 出图 / 改格式 依赖结果栈，通常不再查库
result_action / context_action / skill_execution 简报、监控、技能等动作 交付链 / 工具，须绑 result_id
non_data_request / clarification_required 非查数 / 缺条件要澄清 见下方处置，禁止臆造字段

非查数怎么处置（NonDataDisposition）

· LOCAL_HELP — ChatBI 本地答（怎么用门户、怎么问数）

· RESULT_ACTION — 留在交付链（发简报等），勿误判成「闲聊」

· DELEGATE_MAIN / DELEGATE_WEB — agent_handoff 无感委派；失败才提示「请切换智能体」

要点：外层 Router 只选中 DataQuery；最终判定是 DataQueryTurnClassifier。会话亲和性三态：仅 BREAK 可启发式离开 ChatBI；UNCERTAIN 必须语义路由，不得直接 fallback Main。澄清候选必须来自授权 Schema / 数据集 / 结果栈。

03｜新查数流水线：意图帧 → Schema → SQL

大白话：真要查数时，平台禁止模型一上来就写 SQL。先把用户话翻译成「要查什么指标、什么维度、什么时间、什么粒度」——这叫意图帧；再拿授权范围内的表结构（Schema）；最后才允许执行查询。顺序反了，门禁会直接打回。Schema 不是模型编的——要先在控制台把数据源、元数据集建好并同步，问数才能检索到。

DataQueryIntentFrame（用户需求分析）

结构化记下业务目标、指标、维度、筛选语义、时间范围、粒度等，并派生 Schema 检索词。Trace 上会看到「用户需求分析」卡片。它还是字段绑定自检与空结果修复的依据——空结果不能只因「候选值不含用户原词」就断定没数据。

硬顺序

1. 意图帧 / Schema 预取（失败：无授权、元数据不可用、未同步知识库、连续 miss → 终止）

2. 需要写 SQL 时做 few-shot 案例检索（未命中也要可观测）

3. 必须先 get_dataset_schema，再允许 execute_sql_query

4. 多候选高置信且分数接近 → 先澄清，禁止直接 SQL

Schema 长什么样（get_dataset_schema 命中片段示例）

--- [Schema:1] type=table dataset=sales_ds table=fact_sales score=0.91 --- dataset: sales_ds table_name: fact_sales table_term: 销售明细 columns: - physical_name: sale_date term: 销售日期 type: date - physical_name: region_name term: 区域 type: varchar - physical_name: sale_amount term: 销售额 type: decimal

要点：SQL 里只能用 table_name / physical_name（物理名）；term 是给人看的业务名。数据集级还会有 _metrics.txt 指标口径块（算数参考，不是表结构）。多表命中时用 --- [Schema:n] --- 分隔。

Schema 从哪来：怎么建（运维流程）

ChatBI 运行时不现场扫整库字典，而是检索你事先建好并同步好的元数据。建议按这个顺序：

1. 【数据源管理】登记业务库连接（MySQL / ClickHouse / Oracle…），测通

2. 【元数据管理】创建数据集（Dataset），勾选要暴露的表 / 视图

3. 同步表结构：从数据源拉取物理列；再补 term（业务名）、枚举、指标口径（metrics）

4. 同步到检索侧：执行元数据 RAG 同步（生成表级 chunk + _metrics.txt），供向量 / 本地检索；表结构变更后要重新同步

5. 授权：给用户 / 角色授 dataset（元数据）资源；菜单能进 ≠ 库表可读

6. 挂到 ChatBI：版本工具勾选 schema/SQL；可选工具级 metadata_dataset_ids 收窄可见集（见第 03 篇）

建好了怎么验

· 元数据页「测试 / 检索测试」：用业务词能命中目标表

· 对话问「有哪些销售相关表」→ Trace 见 schema 命中，而不是空召回

· 故意用中文表名写 SQL → 应被拦并引导回 get_dataset_schema

Schema 连续未命中达到阈值 → source_reclassification 来源重判，禁止无限重试查库。模型若在完成查数顺序前输出自然语言结论，最终 guard 会拦截。上限仍看元数据质量：term 乱、指标没写、不同步，护栏拦得了胡写 SQL，补不了脏口径。

04｜SqlQueryBinding 与 SQL 门禁前缀

大白话：Binding 是「工作单」：这张单上写明——你查的是哪张物理表、归属哪个数据集、Schema 长什么样、预检过没过。预检和真正执行共用同一张单，防止「看的是 A 表结构、跑的是 B 表 SQL」。门禁前缀是安检章：没过就不执行，把带前缀的说明还给模型改。

Binding 关键字段

sql · primary_dataset_name · schema_output · tables · preflight_validated 等。
Agent 路径在执行前走 resolve_sql_schema_preflight_with_binding：字段/表与 Schema 一致；Schema 外物理表仅在有元数据权限时放行并回填 dataset。Core 若见 preflight_validated=True 不重复字段校验。

前缀 拦什么 你该怎么做
[SCHEMA_GATE] 未取 Schema / 多候选待澄清 / 字段错误需重取 先 get_dataset_schema；或澄清数据集
[SQL_STATIC_GATE] 非只读、多语句、危险关键字、sqlglot 方言风险 改成 SELECT/WITH 等只读；禁 SELECT *
[SQL_REPEAT_GATE] 同一成功 SQL 再跑一遍 复用首次结果作答，勿空转
[FAILED_SQL_REPEAT_GATE] 失败 SQL 同参死磕 改 SQL / 改 Schema，勿原样重试
[SQL_PLAN_GATE] 高风险要求先过计划 看计划卡片，确认口径后再执行
[TIME_RANGE_GATE] 时间范围不合理 收窄或修正时间条件
[Performance Blocked] 沙箱性能门禁 加过滤 / 限行，避免全表扫描型写法

静态策略偏只读（SELECT / WITH / EXPLAIN / SHOW / DESC）；禁多语句与危险关键字；用 sqlglot 做方言校验。JOIN 须有明确 ON。工具同参无进展会触发循环熔断。

05｜sql_plan 与自愈修复

大白话：计划卡片相当于「手术方案摘要」——目标、表、字段、指标、筛选、时间、粒度、JOIN、风险备注，给人看也给门禁看。SQL 报错或结果是空的，不是让模型瞎重写，而是按修复策略再开一轮：空结果要结合意图帧判断是不是筛错字段、别名、父级范围。

计划 JSON 字段

goal · tables · fields · metrics · filters · time_range · grain · joins · risk_notes
build_platform_sql_plan 基于授权 Schema + 待执行 SQL；前端展示卡片；高风险可强制 [SQL_PLAN_GATE]。

repair_policy

触发：SQL 报错 / 空结果 / 缺计划 → 决策 → 再开一轮 reply_stream

· 执行错误：成功前不得当最终回答

· 空结果：先诊断筛选、时间、JOIN；诊断 SQL 不能当结论

· 比率异常 → 对账复核；时延异常 → 复核时间字段方向/时区/单位

06｜结果栈 · 数据门户 · 简报与订阅

大白话：查成功的每一刀结果会推进「结果栈」，后面说「按城市拆一下」「做成简报」才有据可依——不能让模型凭空编关键数字。数据门户是给业务同学的菜单入口；黄金报表订阅则是「定时再跑一遍 + 通知你」。

结果栈

键名 chatbi_result_stack / data_result_stack_v1（ChatBIResultRef）。SQL 成功后双写兼容键 last_data_result。push_result_ref 最大深度 10。可指「当前 / 上一个结果」或显式 result_id 下钻，条件可继承。简报 / 监控等交付必须绑定可追溯 result_id。

数据门户

斜杠 /dataset_portal（兼容旧 /dataset_menu）；系统指令 id sys_dataset_portal。按用户授权生成数据集菜单 + LLM quick 追问。深链参数如 dataset_portal=1、report_id、run_id。

简报与黄金报表订阅

· 简报 chatbi_briefs：从结果栈沉淀证据化 brief（v2：title / facts / evidence / markdown），可导出 Word；门户 /chatbi-briefs

· 订阅表 portal_saved_report_subscriptions：schedule_type=daily|weekly|monthly|cron；可选 AI 分析、成功/失败通知、external_channels、alert_condition；投递审计 portal_saved_report_digest_deliveries

07｜跨库联邦：自动升级，不靠猜

大白话：一条 SQL 里出现了不属于当前数据集的表，而且牵涉多个库——平台应自动升成「联邦查数」，并用 Binding 把每张物理表钉死到正确的 dataset。不能只靠模型从 Schema 文本里猜库名。

· 单源执行检测到跨 dataset 表引用 → 自动升级联邦（G12）

· 构造 Binding，注入联邦 plan 的【物理表与数据集绑定】块

· 解析子查询后按 Binding 修正 dataset_name；跨库要治理，不是功能开关一开就完事

08｜排障顺序与十分钟验收

大白话：ChatBI 出问题，先别急着改提示词。打开 Trace，按下面顺序从上往下看——八成卡在分诊、门禁或授权，而不是「模型不够聪明」。

推荐排障顺序

1. 智能体是否 CHATBI + 已发布 + 问数工具齐全（见第 03 篇）

2. Trace 分诊类型：是不是根本不该查库？

3. 工具返回是否带 门禁前缀？对着上表改

4. Binding 里的表 / dataset 是否对得上授权元数据

5. 是否进入修复轮、空结果诊断是否合理

6. 数据源连通、元数据同步、RBAC 数据集授权、Few-Shot 案例库

十分钟验收

☐ 问简单计数 → Trace 见 new_data_query + schema 再 SQL

☐ 「换成表格」→ reuse / presentation，不再无故重查

☐ 故意写危险 SQL → 见 STATIC_GATE，不落库

☐ /dataset_portal 能出授权菜单

☐ 无权限用户查不到未授权库表

边界：口径与元数据质量决定上限。Few-Shot 案例库值得运营投入。联邦跨库要治理。已知细节：静态风险门控目前可能先于重复 SQL 门控触发——排障时别被顺序迷惑。

00｜先搞清楚：工具到底是什么

智能体平台 = 大脑 + 手眼 + 记忆 + 编排安全层

大模型本身擅长理解语言、拆解任务和生成计划，但它不能天然读取业务数据库、查看工作区文件、调用公司 API，也不能凭空记住用户上周的偏好。工具就是把模型的“意图”连接到真实系统的可执行接口。

组成它负责什么NanZi 中的例子
大脑：LLM理解问题、规划步骤、选择工具、组织最终回答AgentScope 中的模型调用
手眼：Tools读取、查询、写入、执行、通知，让模型能够观察和行动execute_sql_query、read_file、MCP
记忆：Redis / Markdown / 知识库保存偏好、历史摘要、文档和经验，供后续检索memory_search、RAGFlow、Redis Stack
神经系统：编排与安全控制工具装载、权限、审批、重试、证据和结果回传AgentScope Toolkit、ReAct、Grounding、SQL Gate

用户问题 → LLM 规划 → 选择工具 → 权限/审批预检 → 工具执行 → 结果与证据 → LLM 组织回答

例如“查询本月华东 PUE”：模型不会直接猜答案，而是先找可访问数据集，再取 Schema，必要时参考问答经验，最后执行只读 SQL，并把查询结果作为回答依据。

运行时原理（先记）：业务工具 → RuntimeToolSpec → AgentScope Toolkit → ReAct 调用。静态工具未在智能体版本勾选，模型通常没有入口；隐式运行时工具则可能由系统按场景注入。工具进入调用链后还要过 permission_scope（read/ask/dangerous）、审批模式、用户级 forbidden 黑名单。部分工具成功调用会写入 Grounding 证据类型（内部数据/知识/网页/文件/记忆/运行时）。

先分清三类工具来源

来源例子什么时候出现
静态注册工具execute_sql_query、read_file代码注册后，按智能体版本配置挂载
隐式运行时工具get_current_model、get_current_time由运行时、时间锚点或工具提示策略按场景注入
动态工具已发布 MCP、Generic API控制台配置、同步并发布后进入 Toolkit

所以“工具总数”不能只看 registry.py：静态注册、隐式运行时和数据库动态工具的装载条件不同。

权限边界速查

层级含义典型工具
read读取或检索，通常不改变外部状态get_dataset_schema、search_knowledge_base、read_file
ask可能写入、发送或生成交付物，通常需要用户确认write_file、文档写入、jira_create_issue
dangerous高影响外部执行，还要叠加审批、黑名单和领域安全校验exec_command、manage_process

这不是单一开关：工具白名单决定“能不能看见”，权限级别决定“能否调用”，审批决定“是否放行”，SQL Gate、路径校验和 SSRF 校验负责领域内的最后一道防线。

01｜问数三件套（ChatBI 核心）

get_dataset_schema · 取授权范围内的数据集结构

干什么：按自然语言关键词检索元数据，返回表/字段 YAML（或等价结构），供模型写 SQL 前「看见」真实 Schema。

场景：「PUE」「机房能耗」「华东签单」——先摸有哪些表、字段叫什么，再生成 SQL。

原理：可走 RAGFlow 向量或本地元数据模糊搜；无结果会反馈「换更通用词」。ChatBI 门禁常要求先 Schema 后 SQL；证据类型 INTERNAL_DATA，空成功也可记账。

execute_sql_query · 只读 SQL 执行

干什么：在业务库执行模型生成的查询，返回结构化结果（行数/字节有上限，防把整库灌进上下文）。

场景：一切「查数、同比、明细抽样」；dry_run 可只验 SQL 不执行。

原理：工具层 + ChatBI 外部门禁（SqlQueryBinding、静态风险、重复 SQL、sql_plan 等）。sqlglot 校验；只允许 SELECT/WITH/EXPLAIN/SHOW/DESC 一类只读；禁止多语句与危险关键字。空结果仍可作「暂无数据」证据。

update_dashboard_context · 大屏/前端上下文联动

干什么：让对话驱动前端切换视角（机房、时间窗等），本身多返回成功占位。

原理：执行器拦截成功调用 → SSE context_update → 前端改状态。适合「边问数边控大屏」。

list_accessible_datasets · 列出当前用户可访问且已启用的数据集

干什么：返回已启用数据集的轻量目录（ID、名称、备注、状态），不返回表结构和指标定义；未启用的不会出现。

场景：用户问「我有哪些数据集」「能查哪些数据」时先列目录；确定数据集后，仍要调用 get_dataset_schema 获取字段。

search_qa_examples · 检索已审核的问答经验

干什么：按问题或关键词检索历史优质问答，返回相似问题、数据集和参考 SQL，默认最多返回 5 条。

场景：面对「本月 PUE 同比」「区域签单趋势」等重复分析时，先找相似案例，再结合真实 Schema 生成 SQL；经验案例只能作参考，不能替代权限和 SQL 安全校验。

就绪提醒：CHATBI 类型至少要启用 get_dataset_schema 与/或 execute_sql_query，否则发布/委派门禁不过。

02｜知识库

search_knowledge_base

干什么：在 RAGFlow 知识库检索文档/手册/制度，返回片段供回答与引用。

场景：SOP、制度问答、说明书检索。Knowledge 专家就绪必须挂此工具并绑定 dataset_ids。

原理：按显式 dataset_ids 或智能体配置/默认库解析范围，并过权限。特征关闭时返回禁用错误。Knowledge Runner 还会在 ReAct 前自动预检索。证据 INTERNAL_KNOWLEDGE；空召回也可记账（「未找到」）。

list_accessible_knowledge_bases · 列出当前用户可访问的知识库

干什么：返回知识库目录信息，不返回文档正文，具体检索仍由 search_knowledge_base 完成。

场景：用户问「我能检索哪些文档库」时先列可访问范围，再选择知识库检索；不能根据目录信息臆造文档内容。

03｜任务中心（对话里管 Cron）

以下工具对接 TaskCenter + APScheduler；创建时绑定当前智能体身份与用户。部分属系统隐式工具集，便于助手直接「帮你设个每天 8 点的任务」。

create_recurring_task

参数：name、cron（标准表达式）、prompt（每次执行时给 AI 的指令）、可选 notification_channels（portal/dingtalk/wechat_work/email）。场景：日报、巡检、周报推送。

get_my_tasks / cancel_task / start_task / pause_task / run_task_manually

列表当前用户任务；取消；恢复调度；暂停；立即手动跑一轮。证据上 get_my_tasks 属 RUNTIME_STATE。

04｜消息通知（读用户配置，不钓 webhook）

send_portal_notification — 站内铃铛/Inbox（title、content、level）
send_dingtalk_message — 钉钉（个人中心已配机器人）
send_wechat_work_message — 企业微信
send_email — 邮件（SMTP/收件人来自个人配置）

场景：任务完成摘要、告警、主动提醒。「请用户把 webhook 发给我」是反模式——工具实现故意从用户通知配置取凭据。

05｜Jira 内置集成

jira_search — JQL/关键词搜工单（证据 INTERNAL_KNOWLEDGE，空结果可记账）
jira_get_projects — 列项目
jira_create_issue — 建单（写操作，通常需审批）

场景：运维/研发助手「查缺陷、建工单」。凭据走环境/系统配置中的 Jira 连接，不是让模型记密码。更通用的外部系统优先用 MCP（第 06 篇）。

06｜工作区文件与受控命令（多层安全边界）

这里要区分两类路径边界：普通文件工具主要限制在安全 data 目录、/app/data 或配置的 Skills 目录；Excel/Word 工具则进一步限制在当前用户附件、用户文档目录和会话工作目录。两者都防目录穿越，但不是同一套路径规则。

与 AgentScope 的语义别名对应：read_file≈Read、write_file≈Write、exec_command≈Bash、search_text≈Grep；这不是把宿主机全部文件和命令开放给模型。

read_file — 读文件（offset/limit/tail，单次默认最多 256KB）；证据 USER_FILE
write_file — 完整覆盖写入文件（通常 ask，父目录不存在时自动创建）
search_text — 受控文本检索（支持正则、file_glob、上下文行和结果数量限制）

场景：改配置草稿、读上传附件、在会话产物里搜关键字。目录不能直接用 read_file 读取，应使用 directory_tree_navigator。

exec_command · Shell

执行目录是服务当前工作目录，不等于文件工具的 data 路径范围。命令默认最多运行 30 秒，标准输出和错误输出可能被截断；执行前还会经过删除操作的 ask/deny 策略、危险命令黑名单，以及用户级 forbidden_commands。证据 RUNTIME_STATE。生产环境仍应叠加审批、容器和操作系统权限。

list_process — 列进程
manage_process — 查看或终止指定 PID，仅支持 list / kill（保护平台自身 PID）

场景：查看 CPU/内存占用和进程状态，或终止明确指定的非核心进程；它不是通用的服务启停工具。

几个典型调用（示意参数）

read_file(path="data/uploads/app.log", tail=true, limit=8192)

search_text(pattern="ERROR|Traceback", path="data/logs", file_glob="*.log", context_lines=2)

exec_command(command="df -h")

注意：示例中的命令只用于说明参数形态；删除、写入、终止进程等操作必须明确目标，并按平台审批策略执行。

07｜Skills 相关工具

read_skill_instruction — 读取某 skill 的 SKILL.md 正文
create_skills — 创建/落盘技能包

场景：模型决定「先看看有哪些打法」或「按某技能说明书执行」。主助手还有关键词自动扫描；细节见 Skills 篇。

08｜辅助分析与联网

sqlite_scratchpad

会话隔离的临时 SQLite：可 import JSON 成表再 SQL 清洗/透视，不污染业务主库。目录优先用户私有 sandbox。场景：对查数结果做二次聚合、多表临时 join。

directory_tree_navigator — 目录树浏览
code_syntax_linter — 代码语法检查
web_renderer_and_snapshot — Playwright 渲染/快照页面

fetch_static_web_url — 拉静态页内容（证据 PUBLIC_WEB；版本「联网搜索」组显式配置）
web_search_baidu_http — 百度 HTTP 轻量搜索（中文优先，无浏览器）
web_search_bing_http — Bing HTTP 轻量搜索（英文/国际）
web_search_baidu — 百度 Playwright 搜索（慢通道兜底）
system_http_request — 受校验的 HTTP 请求（method/url/headers/body；URL 有安全校验）

场景：公网资料补充、调内部 HTTP API（无 MCP 时的轻量方案）。联网搜索四件套需在智能体版本「联网搜索」分组显式勾选，不再系统隐式注入。SSRF 等风险靠 URL 校验与权限收紧。

get_current_model — 查询当前实际生效的模型身份和调用阶段，不返回凭据或服务地址
get_myinfo — 读取当前登录用户本人资料、部门、角色与权限，不接受 userid 参数

场景：回答「当前用的是什么模型」「我的角色/权限是什么」时，应读运行时上下文或当前用户，不让模型根据自我描述猜测，也不能读取其他用户信息。

get_current_time / resolve_relative_dates

取当前时间或把「上周」「近 7 天」解析成具体日期。系统隐式工具；证据 RUNTIME_STATE。已有时间锚点时优先复用，避免在同一轮重复取时。

09｜记忆

update_user_preference / fetch_user_long_term_memory / delete_user_preference — 长期偏好读写删（Redis LTM Hash）
memory_search — 按会话摘要/历史向量检索（Redis Stack RediSearch）

场景：「记住我喜欢用表格」「上周我们讨论过的方案」。证据 CONVERSATION_MEMORY；空检索可记账。依赖 Redis Stack。

10｜专家协作

sub_agent_call

干什么：主助手把子任务交给另一个已就绪智能体，收回可交付正文。

原理：校验目标就绪与权限；默认超时约 120s、结果截断、同目标限流；子流程若弹出 permission_required / external_execution_required，委派模式无法代确认，需用户直接打开子专家。输出会清洗 sql_plan 标签防污染父上下文。

11｜办公文档 Excel / Word

excel_document_read（read）/ excel_document_write（ask）
word_document_read（read）/ word_document_write（ask）

场景：读上传表格做分析、生成 Excel/Word 交付物并给下载链接。路径限制在附件/工作区；写操作默认要用户确认。

12｜动态工具（不在静态表里，但同等进 Toolkit）

MCP 已发布工具

名形如 server_name:remote_tool，来自 McpToolCache 且 is_published=True。智能体版本勾选后加载。只读/写倾向可从命名启发式推断，影响 Grounding 外部工具凭证。详见第 06 篇。

MCP 的完整链路：不是“连上 Server 就能用”

① 控制台登记并启用 MCP Server；② 执行 sync，从远端发现工具、参数 Schema 和只读标注；③ 工具写入 McpToolCache，初始通常不是已发布状态；④ 管理员选择工具执行 publish；⑤ 在智能体版本中勾选；⑥ 运行时检查 is_published 与 is_available 后，才把它装入 Toolkit。

名称要注意：平台缓存名可以是 server_name:remote_tool，但为了符合模型 Function Calling 的命名限制，模型侧通常看到的是经过清洗并带哈希的 mcp_... 别名；真正执行时仍转发到远端原始工具名。

MCP 示例：把工单系统接成 Agent 工具

登记 Server：jira
同步发现：search_issues、get_issue、create_issue
发布只读工具：jira:search_issues、jira:get_issue
智能体版本勾选：jira:search_issues
用户提问：查一下项目 OPS 最近一周未关闭的缺陷
模型调用：mcp_jira_search_issues_xxxxx
运行时转发：server=jira，remote_tool=search_issues，arguments={jql: ...}

如果远端工具被删除或同步后变为不可用，平台会把缓存工具标记为不可用，并避免继续把它作为正常工具提供给模型。

Generic API（SysApiTool）

控制台配置 HTTP 接口 Schema → 运行时变成工具，无需改 Python。适合「公司内部一个 REST 就能当 Agent 手脚」。工厂：GenericApiToolFactory。

Generic API 的工作方式：用 Schema 动态生成参数

配置记录包含工具名、描述、HTTP 方法、URL 模板、headers 和参数 Schema。运行时由 GenericApiToolFactory 动态生成 Pydantic 参数模型：URL 中的 {order_id} 会做路径替换，GET 的其余参数作为 query，POST/PUT/PATCH/DELETE 默认作为 JSON body 发送，返回 JSON 或文本结果。

Generic API 示例：查询订单状态

name: get_order_status
description: 查询订单当前状态
method: GET
url_template: https://api.example.com/orders/{order_id}
parameter_schema: {"properties":{"order_id":{"type":"string","description":"订单号"}},"required":["order_id"]}

用户说“查询订单 20260804001”时，模型只需要调用 get_order_status(order_id="20260804001")。平台负责参数校验、HTTP 调用和结果回传；生产环境要特别管理 headers 中的凭据，并限制 URL、方法、超时和返回体大小。

MCP 还是 Generic API？

已有标准化工具协议、需要工具发现和双向会话：选 MCP。
只有一个稳定 REST 接口、希望控制台快速配置：选 Generic API。
需要深度接入平台权限、数据库门禁、Grounding 或复杂业务事务：写平台内置工具，不要把所有逻辑塞进一个通用 HTTP 配置。

13｜怎么扩展 + 安全清单

由易到难：① MCP / Generic API → ② Skill 约束调用方式 → ③ 在 tools/ 用平台 @tool 写函数并 ToolRegistry.register（Docstring 会进模型可见描述）。

如何写一个新工具：从函数到可用能力

① 先定义边界：这是 read、ask 还是 dangerous；② 设计少而清晰的参数，并在 Docstring 写清用途、参数和限制；③ 读取当前用户/Agent 上下文，做权限和业务校验；④ 调用真实 Service，不在工具里直接拼接无约束的数据库或外部请求；⑤ 返回结构化结果和明确错误；⑥ 注册、配置权限与证据类型；⑦ 用单元测试、审批测试和真实 API 调用完成验收。

# 伪代码：查询当前用户有权限查看的工单

@tool
async def lookup_ticket(ticket_id: str) -> str:
    """查询当前用户有权限查看的工单。"""
    ctx = get_current_agent_context()
    if not ctx or not ctx.user_id:
        return "无法识别当前用户"
    if not await can_read_ticket(ctx.user_id, ticket_id):
        return "无权访问该工单"

    ticket = await ticket_service.get(ticket_id)
    return json.dumps({"status": "success", "ticket": ticket}, ensure_ascii=False)

# 注册到运行时；仅注册还不等于所有智能体都能使用
ToolRegistry.register("lookup_ticket", lookup_ticket)
TOOL_EVIDENCE_TYPES["lookup_ticket"] = {EvidenceType.INTERNAL_KNOWLEDGE}

说明：@tool 负责从函数签名生成参数 Schema，ToolRegistry.register 负责运行时注册；还需要导入该模块、配置智能体工具白名单，并由运行时推断或明确设置 permission_scope。

上线前的最小测试清单

□ 正常参数能返回结构化结果　□ 缺少用户上下文会拒绝　□ 越权资源会拒绝　□ 写/危险操作会触发 ask 或 deny　□ 外部服务超时和异常有可读错误　□ 证据类型与返回内容匹配　□ API 层能看到真实工具调用和最终结果

□ 版本只勾真正需要的工具（能力面白名单）
□ 写/危险操作走 ask；用户 forbidden_tools/commands
□ 密钥在系统配置/个人中心，不进 Prompt
□ ChatBI 再叠 SQL Gate，不只靠工具层
□ 需要事实审计时打开 Grounding，看证据类型是否匹配

三个可以照着理解的调用闭环

问数：list_accessible_datasets（不知道有哪些数据集时）→ get_dataset_schema → 可选的 search_qa_examples → execute_sql_query → 返回结果和证据。

知识问答：list_accessible_knowledge_bases（需要选择知识库时）→ search_knowledge_base → 基于返回片段回答并保留引用；没有召回时应明确说“未找到依据”。

定时任务：create_recurring_task → get_my_tasks 确认任务 ID → 按需要 run_task_manually、pause_task 或 cancel_task。

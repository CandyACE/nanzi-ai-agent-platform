在智能体（Agent）生态中，单纯依靠平台内置写死的 API 工具，无法满足千行百业繁杂的外部系统对接需求。Anthropic 推出的 Model Context Protocol (MCP) 为大模型与外部系统之间架起了一座标准化的桥梁。NanZi 平台不仅完整原生支持 MCP 规范，还实现了双通道智能通信、两级灰度发布、全局/个人双作用域以及智能体版本级与会话级动态挂载。本篇将带你从 MCP 的前世今生出发，透视平台架构设计并提供完整的实操指南。

00｜背景与来龙去脉：什么是 MCP？为什么需要它？

大模型连接外部世界的“百团大战”与痛点

在 MCP 诞生之前，各个 AI 平台和框架（如 OpenAI GPTs Custom Actions, Dify Tools, LangChain Tools, Coze 插件）都各自定义了一套 API 规范和 JSON Schema 格式。如果要让大模型调用公司的 Jira、GitHub 或内部 DB：
• 开发者需要为每一个 AI 平台单独编写和维护适配代码。
• 外部系统与平台强绑定，每次 API 变动都需要重新打包部署 AI 平台。
• 安全鉴权、状态保持和长连接在不同平台上体验各异，生态极度碎片化。

MCP 的核心设计理念：AI 时代的“USB-C 接口”

2024 年底，Anthropic 提出了开放的 Model Context Protocol (MCP) 规范。它采用了经典的 Client-Server 架构，将能力抽象为三大标准化原语：

MCP 原语 标准定义 典型应用场景
Tools（工具） 模型可调用的函数/动作，带入参 JSON Schema 创建 Jira 工单、推送 GitHub Commit、发送 Slack 消息
Resources（资源） 只读的上下文数据文件或流，带 URI 标识 读取本地日志文件、抓取数据库 Schema、检索 API 文档
Prompts（提示词） 预定义的交互模板与提示词快捷方式 Standard Code Review 模版、故障排查 Prompt 引导

就像 USB-C 让显示器、鼠标、硬盘共用一条线一样，MCP Server 负责暴露系统能力，MCP Client（如 NanZi 平台）负责统一发现与调度。只要编写一次 MCP Server，就能无缝插入任何支持 MCP 协议的宿主中。

01｜架构视域：MCP 与平台静态内置工具（Tools）的补齐与对比

在前几篇文章中，我们介绍了 NanZi 的静态内置工具箱（如 SQL 查询、本地文件操作、命令执行等）。既然有了内置工具，为什么还需要 MCP？二者在平台中是如何协同补齐的？

全维度对比：静态内置工具 vs 动态 MCP 工具

对比维度 平台静态内置工具 (Built-in Tools) 动态 MCP 工具 (Dynamic MCP Tools)
代码集成与扩展 代码级固化在 registry.py，新增需修改平台发版 零平台代码侵入，仅需在控制台配置 SSE / HTTP URL 即可登记
运行环境与进程 与 NanZi 后端处于同一 Python 运行时进程内 独立进程/网络服务，可运行在任何 Server 或 Docker 容器中
作用域与隔离 全平台公共静态只读定义，按智能体版本勾选使能 支持 global 全局公共 与 personal 个人私有 双作用域
通信与协议 Python async/sync 函数内部内存直接调用 标准 MCP 协议，基于 SSE 或 JSON-RPC 2.0 Over POST 远程过程调用
安全拦截与治理 绑定平台硬核逻辑（如 SQL Gate 语法解析器、只读白名单） 结合对端 Header 鉴权、平台两级发布（Publish）控制与敏感参数审查
典型应用场景 BI 数据库问数、服务器 Shell 执行、工作区文件读写、定时任务调度 GitHub / GitLab / Jira 系统对接、企业私有 API 网关、个人定制小工具

互补定位总结：内置工具是 NanZi 平台的“基石硬实力”，追求性能与绝对掌控力；MCP 工具则是“生态万能适配器”，追求开放性与解耦扩展。两者在 NanZi 运行时中统一汇聚进入 AgentScope Toolkit，模型调用体验完全一致。

02｜NanZi 平台的 MCP 核心设计与通信机制

为了确保第三方 MCP 服务在生产环境下的高可用与安全性，NanZi 平台在底层实现了多项关键机制：

通信引擎架构｜SSE 优先与 Direct HTTP 智能回落机制

[McpSseSession.connect()]
│
├── 1. SSE 探测 (_looks_like_sse_endpoint)
│ ├── 响应为 text/event-stream ➔ 建立标准 SSE 长连接 (mcp.client.sse)
│ └── 10s 超时或报错 ➔ 自动回落降级
│
└── 2. Direct HTTP 智能回落模式 (is_direct_http=True)
├── 对 sse_url 直接发起 JSON-RPC 2.0 Over POST 请求
├── 严格遵循 2024-11-05 协议规范 (initialize ➔ initialized ➔ tools/list|call)
└── 维护 mcp-session-id 响应头与 300s 空闲自动回收

💡 生产硬核设计：现实中很多第三方网关（如 ModelScope、自研微服务）并不提供标准的 SSE 流，而仅暴露出 HTTP JSON-RPC 接口。NanZi 的双通道机制保证了无论对端如何实现，均可开箱即用。

全名命名空间（`server_name:raw_tool_name`）与平滑迁移

不同 Server 可能存在同名工具（如 GitHub 和 GitLab 都叫 create_issue）。NanZi 在同步时自动打上全名标识：github:create_issue。
当管理员在后台修改 Server 名称（如将 git 改名为 github）时，后台 _migrate_server_name_references 会自动平滑更新缓存表及所有已绑定该工具的 Agent 版本配置，避免关联断裂。

两级灰度发布机制（Sync ➔ Publish ➔ ToolRegistry）

• 同步（Sync）：请求远端 tools/list 写入缓存表 sys_mcp_tool_cache。此时工具处于 is_published=False 状态，对智能体不可见。
• 发布（Publish）：管理员测试验证无误后开启发布。开启后触发 ToolRegistry.clear_db_tool_cache()，运行时通过 McpToolFactory 动态转换为 AgentScope 可调用的 Toolkit。

只读/写动作启发式与 Grounding 证据溯源

NanZi 运行时具备强大的防幻觉 Grounding 引擎。对于 MCP 工具，平台通过两条路径判断只读属性：
路径 A（注解显式定义）：读取 Schema 中的 x-nanzi-mcp-annotations 或 readOnlyHint。
路径 B（名称启发式推断）：分析动作谓词，例如 get/list/search/query/read 判为只读，而包含 create/update/delete/send/write 的判为写操作。只读工具调用的返回结果会被自动记入 EXTERNAL_TOOL 证据账本，生成具备可信依据的卡片。

03｜平台实操：如何创建与登记 MCP Server

了解了底层原理后，我们来看如何在 NanZi 平台中一步步创建并上线一个 MCP 服务。

第一步：控制台可视化登记（全局或个人）

• 公共全局 MCP：以管理员身份进入 系统配置 ➔ MCP 服务管理（组件：McpManagement.vue）。配置属于全平台全局资源。
• 个人私有 MCP：普通用户在 个人中心 ➔ 我的 MCP 或对话框挂载栏中配置。仅当前登录用户自己可见。

配置项 示例与说明
Server 名称 github-tools（必须使用纯英文/下划线，作为工具前缀）
SSE / Endpoint URL http://127.0.0.1:8080/sse（支持标准 SSE 或 HTTP Endpoint）
请求头 (Auth Headers) JSON 字符串，如 {"Authorization": "Bearer ghp_xxx"}

第二步：快捷导入 Anthropic 标准 `mcpServers` JSON

如果你手头已有 Claude Desktop 或 Cursor 的配置文件，无需手动拼装！在弹窗中点击「粘贴 JSON 快速导入」，粘贴如下代码：

{
  "mcpServers": {
    "jira": {
      "url": "https://jira.company.com/mcp",
      "headers": { "X-Jira-Token": "secret_abc" }
    }
  }
}

解析工具（parseMcpServersPaste.ts）会自动提取 Server 名称、URL 与 Headers 填入表单。

第三步：连通性在线测试（POST /api/portal/mcp/verify）

在保存之前，点击「测试连接」按钮。后端会触发 verify_mcp_server 接口，生成一个临时 Session (verify_uuid8)，在不影响数据库的情况下向对端握手并尝试拉取工具。若握手成功，将直接回显发现的工具清单；若失败，则提供精准报错日志供排障。

第四步与第五步：同步、发布与控制台试跑（Execute）

• 同步（Sync）：保存后点击「同步工具」，系统触发 POST /servers/{id}/sync 将远端工具写入缓存列表。
• 发布（Publish）：勾选想要暴露给大模型的工具背后的「发布」开关。
• 在线调试（Execute）：展开试跑面板（组件：McpToolTester.vue），输入测试 JSON 参数发起调用（POST /tools/{id}/execute），直观验证 MCP 工具的实际返回值。

04｜平台实操：如何在智能体中使用 MCP 工具

MCP 工具发布后，如何让智能体（Agent）使用它？NanZi 提供了两种使用模式：智能体版本级固定配置 与 会话级动态临时挂载。

场景 A：智能体（Agent）版本级固定配置

适用场景：全团队通用的常态化业务智能体（如“运维小助手”、“DevOps 审计 Agent”）。

操作步骤：
1. 进入 智能体管理，选择目标 Agent 并点击“编辑版本”（组件：AgentVersionEditorDrawer.vue）。
2. 在工具配置分类中展开“MCP 动态工具”。这里会列出所有处于 is_published=True 状态的公共或个人工具。
3. 勾选需要的 MCP 工具（例如 github:create_issue），点击保存并发布新版本。
4. 此时，该 Agent 的所有对话都将默认加载此 MCP 工具。

场景 B：会话级（Session-level）动态临时挂载

适用场景：临时排查或个人专属敏感工具。例如：你希望在一个通用的 Code Agent 中临时挂载你个人的 GitHub Token 对应的 MCP 工具，但不希望改变公共 Agent 的版本定义。

操作步骤：
1. 打开对话窗口（EmbedChat.vue），在输入框下方的资源挂载条（SessionResourceScopeBar.vue）中，点击“MCP 工具”或“个人资源”。
2. 弹出会话级级联菜单（McpCascadeMenu.vue），勾选你私有的 MCP 服务或工具。
3. 勾选后，前端将所选工具写入本会话的 resource_scope.mcp_tools 中。

# session_mcp_tools.py 底层并集逻辑
merged_tools = Agent版本固定Tools ∪ 会话临时mcp_tools

4. 运行原理：后台 session_mcp_tools.py 会自动将该工具以求并集的方式临时注入本次对话的 Agent 运行配置中。会话结束后即销毁，极具灵活性与安全性！

05｜排障清单与最佳实践

高频翻车点与排障步骤

故障现象 常见根因 排查与解决办法
同步成功但对话中没有工具 忘了开启 Publish，或 Agent 版本中未勾选该工具全名 1. 在后台检查工具的 is_published 状态是否为 True。
2. 确认智能体版本或会话挂载栏中已勾选全名（如 github:create_issue）。
测试连接 (Verify) 提示 401 或超时 Auth Headers JSON 格式不合法、Token 失效或 SSE 端口不通 检查 auth_headers JSON 语法；若网关为内网地址，确认 Docker 容器网络可达。查看后端 server.log 中的 HTTP 探测日志。
对话中调用工具提示 Timeout Error MCP 对端处理超时（平台默认 30s），或 Direct HTTP 会话过期 NanZi 具备 Session 过期重试机制。若频繁超时，请排查对端 MCP Server 的耗时逻辑，优化异步处理流程。

最佳实践与关键代码入口速查

• 敏感数据防护：敏感 Authorization Token 请妥善保管在后台鉴权头字段，避免拼接在暴露的 URL 查询参数中。
• 安全黑名单：可结合平台用户级 forbidden_tools 禁止特定高危 MCP 工具。
• 后端代码路径：
  - REST API 控制器：app/api/portal/endpoints/mcp.py
  - SSE / HTTP 客户端引擎：app/services/ai/tools/mcp_client.py
  - 会话级 MCP 注入器：app/services/ai/session_mcp_tools.py
  - ORM 数据表模型：app/models/mcp.py (sys_mcp_servers, sys_mcp_tool_cache)

核心代码路径：app/services/ai/skill_resolver.py · app/services/ai/tools/system_executive_tools.py · app/services/skill_publication_service.py · API /api/portal/skills · /api/portal/skills/personal

如果说系统提示词决定智能体「是谁」，工具（Tools / MCP）决定它「能动手做什么」，那 Skills 就是可版本管理的「怎么干」——把 SOP、约束、检查清单沉淀成一份份 SKILL.md。NanZi 实现了平台 / 个人双轨目录、智能体版本白名单挂载、提及命中与自动扫描、个人技能审核发布到平台库，以及对话内 list / read / create 三件套工具。本篇按「背景 → 架构 → 创建 → 管理审核 → 触发使用 → 工具 → FAQ」展开。

00｜来龙去脉：什么是 Skills？为什么需要它？

过去两年，企业 Agent 走了一条很典型的进化线：先是「会聊天」，接着「会调工具」，再接着发现——会调工具 ≠ 会干活。真正拉开差距的，往往是有没有一套可复用、可评审、可按场景启停的「打法」。Skills 要解决的，正是这一层。

从「全能提示词」到「打法外置」：痛点从哪来？

很多团队第一版落地都是同一个姿势：把客服话术、会议纪要模板、故障分级步骤、合规红线……全部塞进 System Prompt。短期能跑，中期必炸：

• 提示词变成「巨石」：改一句回访口径要动整段 prompt；评审看不懂「哪段管客服、哪段管运维」；A/B 试跑只能整包替换。
• 工具会了，流程不会：模型能发邮件、能建工单、能搜知识库，却不知道「先安抚再取证」「什么级别必须升级值班」「结论前要列待确认项」。
• 经验锁在会话里：高手花半小时摸出一套售后回访话术，关掉窗口就蒸发；新人第二天又从零试错。
• 场景互相污染：故障排障清单与周报结构挤在同一段上下文，闲聊也带着「必须输出风险等级」，成本高、干扰大。
• 治理缺失：谁改的、哪一版生效、能否只对某个 Agent 启用，全靠口头约定。

一个前后对比小故事（售后回访）

没有 Skill 时：用户说「客户投诉物流延误，帮我写回访话术」。模型可能上来就长篇道歉、承诺无法兑现的时效，甚至编造「系统显示已发货」——因为「会写文字」在，但「客服打法」不在。

有 Skill 时：先命中「售后回访」技能 → 按说明书确认投诉类型与情绪级别 → 安抚话术模板 → 收集必要信息清单 → 给出可承诺边界与升级条件 → 必要时再调工单/通知类工具。工具还是那些工具，差别在于步骤与红线被显式写进了可版本文件。

Skills 从哪来？业界在收敛什么？

「把专业流程教给模型」并不新鲜：早期有 Custom GPT 的 Instructions、各类 Bot 的「知识库 + 固定话术」、内部 Wiki 贴进上下文。真正变化的是打包形态与运行时约定逐渐趋同：

• 文件化：不再只是控制台里一段不可 diff 的富文本，而是仓库里的目录 + Markdown。
• 元数据化：YAML frontmatter 描述 id、名称、适用场景（description），方便列表、搜索、自动匹配。
• 可附资源：references、样例、脚本与主说明书同仓，而不是散落在聊天记录。
• 可移植：一份 Skill 包可以在本机 IDE Agent、企业平台、开源 CLI（如 npx skills）之间迁移——NanZi 宿主机映射安装正是接上这条生态链。

可以把它想成厨师的菜谱：灶台和锅铲是 Tools/MCP，厨师人设是 System Prompt，菜谱才是 Skills——同一套厨具，换菜谱就能换出品。

Skills 是什么 · 不是什么

是：给模型看的结构化「打法说明书」——何时启用、先做什么、禁止什么、出错怎么办；可版本管理、可按 Agent / 会话挂载、可审核发布。

不是：
• 不是新的执行引擎（不会替代 ReAct 循环本身）
• 不是权限系统（读了 Skill 也不会自动获得未授权数据集）
• 不是 MCP / 内置 Tools（那些是「能调用的动作」，Skill 是「怎么编排这些动作」）
• 不是知识库全文检索（RAG 回答「资料里有什么」；Skill 规定「这类任务按什么流程做」）

四层对照：Prompt · Skill · Tool · MCP

层级 回答的问题 变更频率 典型载体
System Prompt 你是谁？全局红线是什么？ 低（人格稳定） Prompt Factory / 版本提示词
Skill 这类任务按什么步骤做？ 中（业务 SOP 常改） SKILL.md 目录包
Built-in Tool 平台内置能执行什么动作？ 低（跟发版走） registry.py 静态工具
MCP Tool 外部系统能力如何即插即用？ 中高（业务系统多） MCP Server（见连载 06）

NanZi 里三者叠用：提示词定角色，Skill 定流程与约束，Tools/MCP 落地执行。Skill 约束「怎么做」，不自动扩大「能碰什么」——RBAC、工具审批、工作区隔离等硬护栏仍然生效。

为什么企业 Agent 平台特别需要 Skills？

真实业务天然「流程密集」：客服回访有情绪分级、故障有升级路径、周报有固定结构、主助手还要自动扫描相关打法。如果全靠一条巨石 prompt：
• 改一版客服口径，会误伤闲聊与知识库问答；
• 个人摸索出的回访/排障打法无法沉淀成团队资产；
• 生产环境无法对主助手做「只挂白名单技能」的收敛。
因此 NanZi 做成双轨目录 + 白名单挂载 + 提及/扫描触发 + 审核发布——后面章节逐一展开。先有一个直觉：Skill 是「可插拔的菜谱」，不是「再写长一点的人设」。

01｜NanZi 里的 Skills 架构：平台 vs 个人 · 目录 · 挂载

NanZi 采用双轨目录：平台技能面向全员治理，个人技能落在用户工作区内；运行时再按智能体版本的白名单与会话挂载决定「本轮可见哪些」。同名 id 时，个人覆盖平台。

平台 Skills vs 个人 Skills

对比维度 平台 Skills（global） 个人 Skills（personal）
物理目录 SKILLS_DIR：优先 /app/data/skills，否则 ~/.agents/skills agent_workspaces/{user_key}/skills/{skill_id}/
入口与权限 技能工作台「平台技能」；管理/审核需 element:skills:admin 「我的技能」/ 个人中心；登录即可维护本人目录
典型内容 公司 SOP、客服话术、会议纪要模板 个人习惯、项目专用打法、试验稿
进公共库 管理员直接维护；或审核通过后物化 提交审核 → 通过后生成独立平台 id（不直接改写个人目录）
运行时合并 受版本 skills_custom 白名单约束 始终合并进可见集合；同 id 时覆盖平台

目录结构要点

每个技能一个目录，根上必须有 SKILL.md（可另附 references/ 等资源）。文件头 YAML frontmatter 常用键：id（默认目录名）、name、description、enabled（默认 true）。正文可读路径有 jail：必须落在平台 SKILLS_DIR 或当前用户个人 skills 根下。enabled: false 或门户关闭后，加载与扫描都会跳过。

一份 Skill 长什么样？（伪代码示意）

下面以售后回访为例，是精简伪代码，不是平台内置文件： 

cs-callback-script/
├── SKILL.md
└── references/          # 可选：话术样例、升级矩阵
    └── escalation-matrix.md

# ===== SKILL.md =====
---
id: cs-callback-script
name: 售后回访话术
description: 物流延误/服务投诉类回访；适用于「投诉」「回访」「安抚话术」类请求
enabled: true
---

# 售后回访话术

## When to use
- 用户要写客户投诉回访、安抚话术或升级建议
- 不要用于闲聊、招聘话术或与售后无关的营销文案

## Workflow（伪代码）
1. classify_case(type, severity)     # 物流延误 / 态度 / 质量…
2. empathize(template_by_severity)  # 先共情，再谈方案
3. collect_facts([...])              # 单号、时间、已尝试渠道
4. propose_options(within_policy)    # 只承诺政策内可兑现项
5. escalate_if(severity >= P1)       # 达线则建议建工单/转值班

## Hard constraints
- NEVER 编造物流轨迹或「系统已显示签收」
- NEVER 口头承诺政策外赔偿；不确定就标「需人工确认」
- MUST 区分「可立即答复」与「需升级」两条路径

读法：frontmatter 给扫描/列表用（description 写得越像真实用户说法，自动命中越稳）；正文给模型当 checklist。章节标题可按团队习惯组织（When to use / Workflow / Constraints 只是推荐骨架）。同类写法也可套到会议纪要、故障分级、面试提纲等通识场景。

挂载发生在哪几层？

① 智能体版本级：配置字段 skills_custom。默认 false = 不限制公共技能（前端常显示「全部」）；true 时必须非空 JSON 白名单，只加载勾选的公共 id（个人技能仍合并）。生产主助手建议开白名单，只挂「售后回访」「故障分级」等稳妥技能。
② 会话 / 聊天 UI 级：输入框「+」→ 技能级联菜单（SkillCascadeMenu）可本轮挂载；创建成功横幅支持「立即挂载」。平台没有独立的技能 slash 指令（与 MCP 会话挂载类似，走 UI / 工具链路）。

02｜创建 Skills 的几种方式

NanZi 支持「工作台手工建」「压缩包导入」「对话里让模型沉淀」，以及在宿主机直接安装/克隆、经 Docker 卷映射进容器。选哪条取决于：你是管理员维护公共库、个人先试验再提审，还是对接开源 Skill 生态做本地联调。

方式 A｜技能工作台 · 空白新建

进入技能工作台 →「新建技能」→ 填写 id / name / description，系统生成目录与初始 SKILL.md，再在文件树中编辑正文与附属资源。当前 Tab 决定写入平台库还是个人库（平台侧写操作需管理权限）。

方式 D｜宿主机安装，映射进容器

Docker 部署时，平台技能与工作区数据通过卷挂进容器，因此你可以在宿主机终端用 CLI / Git 装好 Skill，容器内的 NanZi 立刻能扫到，无需再走上传表单。compose 典型映射：

~/.agents/skills  →  /app/data/skills
./data            →  /app/data

D1 · 平台全局技能（npx CLI）

平台目录映射到宿主机 ~/.agents/skills/。可在本机用开源 npx skills 从外部仓库拉取全局技能，例如：

$ npx skills add https://github.com/vercel-labs/skills --skill find-skills

D2 · 个人专属技能（Git clone）

个人技能落在 agent_workspaces/{user_key}/skills/{skill_id}/。因 ./data 已挂到 /app/data，本地开发可把离线 Skill 仓直接克隆到用户隔离目录：

git clone [仓库地址] ./data/agent_workspaces/[user_key]/skills/[skill_id]

目录内仍须有合规 SKILL.md；user_key 与登录用户一致，否则工作台「我的技能」看不到。改完后刷新技能列表即可，一般不必重启容器（文件落在挂载卷上即时可见）。

03｜管理与审核：启停、统计、发布流水线

日常管理

技能工作台支持列表/卡片视图、按名称或时间排序、启停开关、文件树编辑、资源上传。登录用户可打开调用统计（只读：分布与趋势来自 Redis 激活记录，接口不要求 admin）。平台技能的增删改、以及「待审核」Tab，仍由 element:skills:admin 控制。

个人 → 平台：审核步骤

1. 在个人技能上点「提交为平台技能」（已发布过可「提交新版本」）。
2. 系统生成只读快照版本，状态 PENDING，并向具备审核权限的管理员发站内信。
3. 管理员在「待审核」：通过 → 物化为独立平台 Skill（PUBLISHED）；驳回 → REJECTED（需填原因）；提交人也可在 PENDING 时撤回（WITHDRAWN）。
4. 个人原目录仍保留，便于继续改；平台侧与个人侧 id 可隔离，避免同名踩踏。

状态速查

状态 含义
UNPUBLISHED 尚未进入审核 / 撤回后回到未发布
PENDING 待管理员审核
PUBLISHED 已物化到平台库，可供版本白名单挂载
REJECTED 已驳回，可改稿后再次提交
WITHDRAWN 提交人主动撤回待审版本

重要：审核通过不会自动把新平台技能塞进已有 Agent 版本的白名单。仍需在对应版本勾选并回归验证，避免「库里有了但对话永远扫不到」。

04｜如何使用 / 触发 Skills

运行时由 skill_resolver 决定「本轮激活哪些技能摘要 / 全文」，再注入提示词中的 [Active Skills Loaded] 区块；模型按摘要或预载全文执行，必要时再调工具读全文。下面用具体话术说明四种触发方式。

resolve_skills_from_query · 提及命中

用户话里出现「使用 XX 技能」等模式，或显式点名技能名/id。匹配分：精确名/id ≈1.0，子串名 0.9，id 0.85，描述 0.7；默认阈值 ≥0.7，最多约 2 条。

可照抄的用户话术示例：

• 「使用售后回访技能，客户投诉物流延误，帮我写安抚话术」
• 「按 meeting-minutes 技能走一遍，把这段录音纪要整理成决议+待办」
• 「用一下我的 周报生成 技能，把本周进展收成周五周报提纲」
• 「启用技能 incident-triage，先分级再决定是否通知值班」

scan_relevant_skills · 自动扫描

用户没点名，但问题像某套 SOP 时，由主助手（id 如 sys-agent-chat，或 slug assistant / main / general-chat）自动扫描。配置项：skill_auto_scan_enabled（默认 true）、skill_auto_scan_min_score（默认 0.45）、max_results 默认 1（钳制 1–3）。过短/寒暄不扫；个人技能略加分。

场景示例（假设库里有 description 写清场景的技能）：

• 用户：「帮我写一份售后回访话术，客户投诉物流延迟」→ 可能扫中 cs-callback-script
• 用户：「机房巡检发现一台服务器温度偏高，按标准流程处理」→ 可能扫中 dc-incident-sop
• 用户：「你好」/「在吗」→ 不扫（寒暄短路）

全文预加载

高相关时把 SKILL.md 正文预注入，减少再调 read_skill_instruction。skill_auto_full_load_enabled 默认 true；扫描路径需分 ≥ skill_auto_full_load_min_score（默认 0.75）；条数与字节有上限（默认约 64KB，上限 256KB）。提及/已挂载路径可更积极满载。

例子：用户说「使用售后回访技能写物流延误安抚话术」且命中分很高 → Active Skills 里直接带上完整 workflow（分级 → 共情 → 取证清单 → 可承诺边界），模型可不先调 read，直接按步骤组织回复；若只注入了摘要，你会在思考链路里看到随后的 read_skill_instruction。

会话里手动挂载

聊天输入区「+」打开技能级联：选个人或平台可见技能，本轮挂载后进入 Active Skills。适合「这轮明确要按某本手册执行」，比赌自动扫描更稳。

操作示例：① 点「+」→ 技能 → 勾选「售后回访话术」；② 再输入「客户投诉物流延误，帮我写回访」。即使话里不提「技能」二字，本轮也会带着该 SKILL 的约束（先共情、不编造轨迹、政策外赔偿需确认等）进入执行链。

05｜与 Skills 相关的工具指令

三个工具需在智能体版本的工具列表中勾选后，模型才能调用。下面按「用户怎么说 → 模型通常调什么」给出例子（参数名以平台注册为准）。

list_available_skills

列出当前可见技能的 id / name / description / scope。尊重 skills_custom 与 disabled。模型「先盘点再选型」时用。

用户可以这样说：

• 「你现在能用哪些技能？列一下名称和用途」
• 「有没有和周报、回访、故障分级相关的技能？」

模型侧示意调用：

list_available_skills()

read_skill_instruction(skill_id)

读取指定技能 SKILL.md 全文（有字节上限与路径 jail）。Active Skills 仅摘要、或需刷新核对时必须调用；已预载全文时可按提示直接执行。

用户可以这样说：

• 「先读一下售后回访技能的完整说明，再帮我写话术」
• 「把 incident-triage 的步骤原文贴给我看看」

模型侧示意调用：

read_skill_instruction(skill_id="reconciliation")

create_skills(...)

对话内创建技能文件；默认写入个人库。需在智能体版本工具列表中勾选该工具才会出现在模型可调用集合中。

用户可以这样说：

• 「把刚才这套『先共情再取证再给方案』的回访打法存成个人技能，叫 my-cs-callback」
• 「根据我们刚确认的巡检步骤，创建技能：名称机房巡检 SOP，描述写清适用巡检告警」

模型侧示意调用（字段示意）：

create_skills(
  skill_id="my-cs-callback",
  name="我的回访打法",
  description="投诉回访：先共情、再取证、只承诺政策内方案",
  skill_md_content="---\nname: ...\n---\n## Workflow\n1. ...",
  scope="personal"
)

成功后流里会出现 NANZI_SKILL_CREATED:…，前端可弹出「去编辑 / 立即挂载」。

工具组合：一轮「不知道有没有合适技能」

用户：「处理客户投诉物流延迟，按标准流程来」
① list_available_skills() → 发现 cs-callback-script
② read_skill_instruction(skill_id="cs-callback-script")
③ 按 SKILL 步骤组织回复 / 调业务工具（仍过权限与确认卡）

提示词侧约定（摘要）

• 已匹配且预载完整指令 → 直接按 SKILL.md workflow 执行。
• 已匹配但仅摘要 → 先 read_skill_instruction。
• 未匹配但可能需要 → list_available_skills → 再对最具体匹配的一个 read。
实现参考：agent_prompts.py · system_executive_tools.py · registry.py

06｜补充与 FAQ

常见问题速查

现象 常见原因 怎么处理
对话从不触发某平台技能 版本开了 skills_custom 但未勾选；或 enabled=false 检查版本白名单与启停；或会话「+」手动挂载；显式说「使用 XX 技能」
审核通过了但仍扫不到 发布≠自动进白名单 到目标 Agent 版本勾选新平台 skill_id 并保存发布
专家智能体不自动扫描 自动扫描仅主助手开启 用提及 / 会话挂载；或在该专家版本绑定工具让模型主动 list/read
create_skills 写不进平台库 非 admin 用户写 global 被拒 先写 personal，再走提审；或由管理员在工作台创建
同 id 行为「怪怪的」 个人覆盖平台 检查个人目录是否残留同名技能；发布物化时用独立平台 id
Skill 能绕过权限吗？ 不能 Skill 只影响模型怎么想；工具与资源仍过 RBAC、审批等硬护栏

最佳实践与代码速查

• description 写场景词：扫描靠名称/描述相关度，别只写「通用助手技能」。
• 生产开白名单：主助手 skills_custom=true，只挂评审过的公共技能。
• 个人试验 → 提审 → 版本挂载：三步不要跳。
• 解析与扫描：app/services/ai/skill_resolver.py
• 对话工具：app/services/ai/tools/system_executive_tools.py
• 发布审核：app/services/skill_publication_service.py
• 门户 API：app/api/portal/endpoints/skills.py · personal_skills.py

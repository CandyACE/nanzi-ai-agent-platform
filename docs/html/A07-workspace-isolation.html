项目声明

核心代码路径：app/services/ai/runtime/agentscope/workspace.py · app/utils/fs_access.py · app/utils/fs_paths.py · app/api/v1/endpoints/fs.py · app/services/ai/runtime/shell_deletion_policy.py

当大模型智能体从单纯的“文字聊天”进化为具备真实生产力的“数字员工”时，它必须拥有读写文件、执行脚本、生成报表和调用 Shell 命令的实操能力。然而，在企业多用户并发环境下，一旦为 Agent 开放底层文件系统与执行权限，随之而来的就是极其严峻的安全挑战：如何防止用户 A 的助手偷看用户 B 的机密文件？如何杜绝模型误操作对宿主机系统的破坏？会话产生的临时数据如何安全隔离与销毁？
NanZi 平台构建了从“Docker 宿主机物理隔离 → 多租户专属工作区 → 会话级运行时沙箱 → 提示词认知引导 → 云端第三方 Sandbox 扩展”的完整纵深防御体系。本篇将全面拆解这一硬核安全架构。

00｜背景与核心挑战：四层纵深防御安全防线

开放文件与 Shell 执行的四大安全风险

在企业级场景中，AI 必须能完成“阅读用户上传的 Excel → 编写 Python 脚本分析 → 生成 PDF 简报并落盘”这一整套操作。若缺乏完善的隔离机制，将面临：
• 宿主机破坏风险（Host Compromise）：命令直接在宿主机执行，模型误删宿主机系统文件或窃取主机环境密钥。
• 跨租户越权（Cross-Tenant Leakage）：恶意 Prompt 诱导 Agent 读取 ../../other_user/ 目录下的敏感凭证或数据。
• 工作目录混淆（CWD Collision）：多用户同时执行脚本时，相对路径相互覆盖，造成数据污染。
• 破坏性误操作（Destructive Actions）：模型偶发幻觉执行 rm -rf / 或清空全平台存储。

NanZi 平台的四层纵深防御隔离架构

防线层级 核心技术载体 隔离机制与防御目标
第 1 层：容器物理隔离 Docker 容器边界 推荐 Docker 部署，所有命令在容器内运行，宿主机 OS 与外部业务物理不可达
第 2 层：多租户空间隔离 fs_access.py / fs.py 用户专属 agent_workspaces/{user_key} 目录，API 白名单与 realpath 防越权
第 3 层：会话运行时沙箱 AgentScope LocalWorkspace 每个会话绑定专属 CWD 沙箱，原生文件/Bash 工具重定向，Prompt 注入路径约束
第 4 层：云端计算沙箱扩展 第三方 / 云端 Sandbox 接口 接口预留支持将 Bash/Python 调度至独立 Docker 沙箱容器、MicroVM 或云端 Serverless 执行

NanZi 平台的数据存储物理根目录位于容器内的 /app/data（或本地开发目录 data/）。所有用户的文件资产统一规整在 data/agent_workspaces/ 根节点下。

02｜API 与文件系统安全访问控制（fs_access.py & fs.py）

前端文件管理、附件预览与内容编辑统一由 /api/v1/fs 系列接口提供。底层通过 app/utils/fs_access.py 实施严格的 RBAC 与路径校验：

1. 授权根目录白名单（`get_allowed_fs_roots`）

• 普通用户（user）：系统动态计算可访问根目录列表 = [公共数据目录 (branding, skills), 本人私有工作区 (agent_workspaces/{user_key})]。访问其他路径均直接触发 403 拦截。
• 系统管理员（admin）：具备 /app/data 完整沙箱的运维与审计权限。

2. 严格的读写分离防护（`assert_path_writable`）

公共目录（如全局技能包、平台静态资源）对普通用户仅开放只读访问。新建文件、写入内容、重命名或删除等修改动作，通过 assert_path_writable() 进行强校验，只允许写入当前登录用户的私有工作区内，防止恶意篡改公共设施。

3. 路径规范化与符号链接防逃逸（`normalize_fs_path`）

为了防御利用 ../../ 相对路径穿越或 Linux 符号链接（Symlink）绕过权限校验的行为，平台在鉴权前统一调用 os.path.realpath() 解析真实物理路径，确保判定基准真实可靠。

03｜Agent 运行时沙箱：AgentScope LocalWorkspace 深度集成

在后端执行层，NanZi 深度集成了阿里开源的 AgentScope 2.x 运行时。智能体在思考和行动时，平台如何将文件工具安全收敛至会话沙箱中？

AgentScope 运行时工作区装配流程（workspace.py）

[用户触发对话 (user_id, conversation_id)]
│
├── 1. 动态定位会话工作目录 (resolve_session_workdir)
│ └── workdir = /app/data/agent_workspaces/{user_key}/sessions/{conversation_id}
│
├── 2. 双轨技能路径扫描 (discover_platform_skill_paths)
│ ├── 全局技能包：/app/data/skills/ (按白名单过滤)
│ └── 本人私有技能：/app/data/agent_workspaces/{user_key}/skills/
│
├── 3. 初始化并缓存 LocalWorkspace 实例
│ └── LocalWorkspace(workdir=workdir, skill_paths=[...])
│
└── 4. 工具重定向与 CWD 绑定 (bind_configured_tools_to_workspace)
├── 将智能体配置的 Bash、Read、Write、Edit、Glob、Grep 绑定至该工作区
└── Bash 启动目录天然锁定为 workdir，会话隔离开箱即用！

原生工具重定向与生命周期缓存

• 动态重定向：NanZi 不直接使用裸机 Python 函数，而是利用 bind_configured_tools_to_workspace 把模型调用的文件工具替换为与当前会话绑定的沙箱实例。这意味着大模型编写代码执行 open("output.csv", "w") 时，文件必然安全写入该会话的 sessions/{conversation_id}/ 目录下，绝不污染系统和其他会话。
• Workspace 高性能缓存：通过 _workspace_cache 按 workdir::skills_hash 维护内存实例，避免单会话多轮对话中重复初始化的开销。

04｜计算隔离进阶：从 Docker 容器物理边界到云端扩展 Sandbox

除了文件系统逻辑隔离，算力执行环境的物理边界是保障平台绝对安全的基石：

1. Docker 容器物理边界：彻底避免对宿主机的危险破坏

• 官方推荐生产部署方式：NanZi 官方强烈推荐采用 Docker 容器化部署。
• 宿主机零侵入：Linux Namespace（PID、MNT、NET）与 Cgroups 机制把大模型执行的所有 Bash 进程与 Python 脚本完全封锁在容器内部。
• 物理防御底线：大模型在容器内执行的任何命令、创建的任何中间进程，均无法逃逸触碰宿主机的底层操作系统与宿主业务，从根本上消除了破坏宿主机的灾难性风险。

2. 架构前瞻：接口预留与第三方 / 云端 Sandbox 扩展

在面对金融、政企等高合规场景中不可信 Python/Shell 脚本的深度执行需求时，NanZi 在执行器接口层进行了可插拔解耦设计：

[NanZi 控制面 (Agent Orchestration)]
│
├── 本地默认：Docker 容器内 LocalWorkspace 执行器
│
└── 扩展接口：第三方 / 云端 Sandbox 适配器 (Remote Sandbox Provider)
├── 独立 Docker Sandbox 容器集群（多租户即起即毁）
├── 轻量级 MicroVM（如 Firecracker / Kata Containers）
└── 云端 Serverless 安全沙箱（如 E2B、Modal、云厂商计算沙箱）

通过将“智能体编排控制面”与“代码执行数据面”在物理上完全分离，实现高危代码秒级容器拉起、网络外呼精细化拦截以及执行完即焚，提供极致的安全隔离能力。

05｜Prompt 软引导与 Shell 破坏性硬防护

除了底层系统沙箱，NanZi 还在“大模型认知层（Prompt）”与“命令行执行层（Shell Policy）”构筑了双重安全门禁：

认知层引导：自动注入 [Session Workspace & Path Sandbox] 规则

当智能体挂载了文件或命令工具时，系统在运行时会自动向 System Prompt 中注入沙箱说明（见 AgentServicePrompts.session_workspace_sandbox_block）：

[Session Workspace & Path Sandbox]
• 会话工作目录：/app/data/agent_workspaces/{user_key}/sessions/{cid}
• 默认文档目录：/app/data/agent_workspaces/{user_key}/docs
• 严禁访问其他用户或其他会话的 agent_workspaces 目录；不得臆造路径。
• 用户要求交付持久文档但未指定路径时，默认写入 docs/ 目录。

大模型在拥有清晰路径心智后，能主动将临时文件与交付物分门别类存放，大幅减少由于路径不明确引发的执行错误。

执行层硬防护：Shell 受保护根目录与删除拦截策略

在 shell_deletion_policy.py 中，平台构建了受保护根目录清单（Protected Roots）：
• /、/app/data、/app/data/agent_workspaces 以及用户主目录均为绝对保护根。
• 拦截判定（deny）：任何试图递归删除受保护根目录的命令（如 rm -rf /app/data/agent_workspaces）均会被即时阻断并告警。
• 二次确认（ask）：针对具体工作区文件的批量删除，系统可根据安全配置挂起并要求用户在界面上点击确认后方可继续执行。

06｜端到端数据流转与生命周期实战

典型文件流转全链路（从附件上传到报表落盘）

1. 用户上传附件：用户在前端上传 sales.xlsx，后端清洗后暂存至 agent_workspaces/{user_key}/uploads/sales.xlsx。
2. Agent 演算分析：AgentScope 在会话工作目录 sessions/{cid}/ 下执行 Python 脚本读取附件，清洗数据并生成临时图表。
3. 报告落盘交付：Agent 将最终整理好的 sales_report.md 写入用户持久化文档目录 docs/sales_report.md。
4. 会话生命周期终结：当用户在界面删除该历史会话时，memory_service.py 自动调用 delete_workspace_for_session，仅物理清理该会话对应的 sessions/{cid} 临时目录并释放内存缓存，用户的持久报告（docs）与历史上传附件（uploads）完整保留！

工作区与文件隔离高频排障清单

故障现象 常见根因 排查与解决办法
API 提示“安全越权拦截 403” 请求路径不在公共目录或本人私有工作区内，或使用了非法相对路径 确认当前登录用户身份；检查前端传递的路径是否越界。普通用户不可直接访问 /app/data 根节点。
AI 声称写了文件但 docs 中没有 模型使用了相对路径写入了会话临时目录 sessions/<cid>/，未写入 docs/ 在文件浏览器中检查对应的会话目录；或在对话中明确要求“将文件保存至我的文档目录”。

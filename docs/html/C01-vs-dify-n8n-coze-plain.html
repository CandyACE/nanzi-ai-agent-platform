NanZi vs Dify / n8n / 扣子

不是比谁更火，而是比谁更适合你的企业场景

项目声明

本项目为个人开源，供自由学习交流，遵循 MIT 开源协议，可自由分发。

「NanZi」来自我一直使用的网名（南孜），取「孜孜不倦」之意。仓库： RandyChen1985/nanzi-ai-agent-platform

做企业智能体选型时，同事常会问同一句：「你们跟 Dify、n8n、扣子（Coze）比，差在哪？强在哪？」

这四个产品其实不在同一条赛道上——有的偏 LLM 应用编排，有的偏自动化工作流，有的偏 C 端 Bot 与渠道分发，NanZi 则更接近企业级多智能体编排中枢：对话只是入口；内置通用 / 企业级 ChatBI / 知识库三类专属智能体引擎，再叠权限、审计、调度与嵌入，才是主干。

本篇是连载盘外加餐：不黑同行、不堆功能清单，只帮你把「选什么」想清楚。读完应能回答：我的团队更像哪种买家；NanZi 真正拉开差距的能力在哪几块。

一句话结论：要快速搭 Bot / 工作流 / 渠道分发，Dify、n8n、扣子各自很强；若目标是私有化落地 + 通用/ChatBI/知识库三类专属引擎 + 权限/审计/嵌入业务系统，NanZi 的产品形状会更贴。

01｜先对齐：四个产品各自是什么

NanZi · 企业智能体编排中枢

开源（MIT）、可私有化部署。本地 AI 跑在 AgentScope ReAct 上，并内置三类专属智能体引擎：通用智能体（工具链 / 写作 / 通知 / 任务）、企业级 ChatBI（元数据、SQL 护栏、自愈、数据门户、黄金报表）、知识库专属智能体（授权检索、引用与 Grounding）。还可混编 RAGFlow / OpenClaw 等外部引擎；再加上 MCP / Skills、调度通知、Embed / V1 API，以及贯穿全链路的 RBAC、工作区隔离、工具审批与 Token 额度。

Dify · LLM 应用与工作流平台

面向「把大模型做成应用」：Chatbot、Agent、Workflow、知识库、插件市场。上手快、可视化强、社区与模板丰富，适合产品/研发快速验证对话应用与 RAG。企业侧可自托管，但核心叙事仍是LLM App 工厂，不是专为经营问数与数据治理打磨的中枢。

n8n · 自动化工作流引擎

更接近「开源版 Zapier」：节点多、集成广、定时与事件驱动一流。适合把 API、数据库、消息系统串成流水线。近年也接 LLM，但基因是流程自动化——对话式多智能体、企业问数护栏、专家路由，不是它的主战场。

扣子 Coze · Bot 创作与渠道分发

字节系产品，强项是低门槛搭 Bot + 多渠道发布（抖音、飞书等生态友好）。适合运营/产品快速做出可发布助手。企业私有化、复杂数仓权限、深度二次开发与审计，通常不是其首要设计目标；数据与能力边界也更依赖平台侧策略。

02｜六个维度对照（选型用）

下面用「更适合 / 够用 / 非主场」定性，避免假精确打分。真实项目还要看团队栈、合规、已有资产。

① 核心定位

· NanZi：通用 / ChatBI / 知识库三类专属引擎 + 编排治理与嵌入

· Dify：LLM 应用 / Agent / Workflow 工厂

· n8n：跨系统自动化编排

· 扣子：Bot 创作与渠道分发

② 企业问数（Text-to-SQL）

· NanZi：原生强项——元数据 / Schema 门禁 / SQL Gate / 自愈 / sql_plan / 数据门户 / 黄金报表订阅

· Dify：可接工具与工作流拼查数，深度护栏与连续分析需自建

· n8n：适合固定 SQL/API 流水线，不适合自然语言多轮经营分析

· 扣子：可接插件查数，企业口径治理与私有数仓深度一般非主场景

③ 权限 · 隔离 · 审计

· NanZi：RBAC（系统/资源/菜单元素）+ 用户工作区隔离 + 工具审批/黑名单 + Skills/API 白名单 + Trace / Grounding + Token 额度

· Dify：工作区与权限可用，偏应用级；数据行级、SQL 硬门禁需自行补齐

· n8n：凭据与工作流权限成熟，对话侧「人-数据-工具」细粒度治理非主叙事

· 扣子：平台账号体系为主，私有化细粒度治理取决于部署形态

④ 编排形态

· NanZi：意图路由 / @专家 / 多专家合成；本地 ReAct + 外部引擎混编；主助手委派

· Dify：可视化 Workflow + Agent 节点，编排体验优秀

· n8n：节点图编排王者，适合确定性流程

· 扣子：工作流 + 插件 + 多 Agent，面向 Bot 场景友好

⑤ 嵌入业务系统 / 运维闭环

· NanZi：Embed SDK（postMessage）+ V1 API；Cron 任务中心；站内信 / 钉钉 / 企微 / 邮件；场景模板与工作台

· Dify：API / 嵌入可用，企业门户与报表订阅需二次拼装

· n8n：Webhook / 调度极强，聊天 UI 与专家工作室需另搭

· 扣子：渠道分发强；嵌进自有 ERP/BI 门户通常要额外适配

⑥ 部署与数据主权

· NanZi：个人开源 MIT，Docker / 源码私有化；依赖 MySQL + Redis Stack + 自备 LLM

· Dify：开源自托管成熟，也有云服务；社区活跃

· n8n：开源自托管友好；企业版另有商业能力

· 扣子：以平台服务为主；企业版/私有化需按官方方案评估

03｜NanZi 真正拉开差距的五件事

别人也能「接个数据库工具让模型写 SQL」。NanZi 的差异不在「能不能查」，而在查得是否可控、能否进入日常经营节奏。

① 企业 ChatBI 是一等公民，不是插件

从元数据与案例 Few-Shot，到 Schema 授权、SQL Gate、空结果诊断与自动修复、结构化 sql_plan 卡片，再到数据门户、业务简报、黄金报表钉选与订阅——这是一整条问数交付链，不是对话框里挂一个「execute_sql」。

业务同学问「本月华东签单同比」，要的是可信数字、可下钻、可订阅，而不是一次抽奖式生成 SQL。

② 治理写进运行时，而不是写进提示词

「请遵守权限」这句话挡不住越权。NanZi 把 RBAC、数据集授权、工具 permission_scope / 审批、用户级禁止工具与命令、工作区文件系统隔离、Token 额度，做成运行时闸门；Grounding 再给对话侧补一层证据账本。

企业落地时，往往是权限与隔离先卡住，而不是模型选哪家。

③ 三类内置引擎 + 可混编外部大脑

本地不只「通用 Agent」：产品主类型就是 GENERAL / CHATBI / KNOWLEDGE_BASE 三条专属引擎，各自带就绪门禁与能力面，统一跑在 AgentScope 上。已有 RAGFlow 资产可挂托管 Agent；需要安全网关与数据集 ACL 时可走 OpenClaw——统一入口、统一鉴权叙事，内置专家 + 外部引擎可混编。这不是「再做一个 Agent 页面」，而是编排中枢。

④ 工具 · Skill · 调度 · 通知拧成一条运维闭环

工具是手，Skill 是打法，调度是班车，通知是喊人。NanZi 内置办公文档、MCP、个人/平台 Skills、APScheduler 任务中心、四通道通知，让「早报、巡检、黄金报表告警」可以无人值守，而不是每次人工打开对话框。

⑤ 嵌进现有系统，而不是逼业务搬家

Embed Chat SDK 用 postMessage 握手，对接现有鉴权与租户；V1 API 给服务端编排。助手长在 ERP、数据门户、知识库旁边，而不是再开一个「只有 AI 自己的世界」。

系列金句：会聊天只是起点；会查数、可审计、嵌得进业务，才是企业智能体。

04｜怎么选：诚实决策树

更建议选 NanZi，如果你……

· 核心痛点是经营问数 / 制度问答 / 多专家协同，而不是先做一个营销 Bot

· 必须私有化，数据、权限、审计要握在自己手里

· 已经有（或计划有）数仓 / 业务库，需要 Schema 门禁与 SQL 护栏

· 要把助手嵌进现有业务页，并接受开源二次开发

· 需要定时简报、报表订阅、钉钉/企微通知这类运维闭环

更建议选 Dify，如果你……

要快速搭 LLM 应用与可视化工作流、重度依赖社区模板与插件生态、团队以「做对话产品」为主、问数深度可以后补。Dify 在 LLM App 工厂这条路上非常成熟——NanZi 并不试图在「拖拽工作流编辑器」上硬刚。

更建议选 n8n，如果你……

主需求是系统间自动化（同步、审批流、告警管道），对话只是偶发一环。很多团队甚至会：n8n 跑确定性流程，NanZi / Dify 扛智能对话——它们可以互补，而不是互斥。

更建议选扣子，如果你……

要快速做出可在抖音 / 飞书等渠道发布的 Bot，运营同学要低代码上手，且能接受平台侧能力与合规边界。面向 C 端增长与内容生态，扣子往往更「开箱即用」。

05｜NanZi 的边界（也写清楚）

· 不是免运维 SaaS：需要 MySQL、Redis Stack、自备 LLM；知识库 / 部分 ChatBI 链路常依赖 RAGFlow。
· 不是纯拖拽工作流 IDE：编排重心在专家路由、工具与 Skill，复杂确定性流水线可交给 n8n。
· ChatBI 上限看元数据质量：护栏防越权与胡写 SQL，不替你补错口径。
· Grounding 降低无依据胡说，不承诺零幻觉。
· 个人开源：适合学习、二次开发与私有化试点；商业 SLA / 大规模多租户要自己评估运维能力。

能力边界写清楚，比堆砌「全面超越」更涨信任——这也是连载一贯的写法。

06｜收束：编排智能，连接数据

Dify 擅长把模型做成应用；n8n 擅长把系统连成流水线；扣子擅长把 Bot 发到渠道；NanZi 想做的是：在企业墙内，把数据、专家、工具、权限、调度编排成可审计的智能中枢。

选型没有唯一正确答案。若你的下一句话是「我们要周末把助手跑起来，先查清本月经营数，再嵌进门户」，欢迎从仓库与实战连载起步。

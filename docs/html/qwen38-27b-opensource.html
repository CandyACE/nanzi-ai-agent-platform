开源模型观察 · 开源当天实测

Qwen3.8-27B 今天开源：第一时间上手，看看它到底怎么样

从模型特性、官方评测到单卡部署实践

就在今天，通义千问开源了 Qwen3.8-27B；几天前发布的 2.4T Max 则面向集群。对大多数需要自建服务的团队来说，更现实的问题是：27B 能否在单卡上把视觉输入、长上下文和 Agent 任务能力跑起来？它采用 Apache 2.0 许可，现已可从 Hugging Face 和 ModelScope 获取。

这篇文章分四步：先看模型结构，再把官方分数放回测试条件，然后给出一套单卡部署方式，并以 H 系列为例落到具体命令，最后用 EvalScope 做压力测试。SGLang 已经提供了对应的部署 cookbook。

文章会把模型介绍、评测条件和部署实践放在一起看。模型卡上的分数只用于判断能力方向，不等同于线上吞吐；上线前仍要用自己的任务、工具链和并发规模复测。

# 本文采用的部署组合

单卡 · FP8（以 H100 / H800 / H200 为例）
SGLang · 权重内 MTP（EAGLE 3/1/4）· qwen3 / qwen3_coder 解析器

01｜先看模型：27B 的能力从哪里来

Qwen3.8-27B 的架构底座是 Qwen3.5，服务路径与 Qwen3.6-27B 一样，走 SGLang 的部署链路。虽然名称是 27B，Hugging Face 上的张量规模约为 28B，但它仍然按单卡稠密模型来规划显存。

关键规格

· 形态：稠密因果语言模型 + 视觉编码器，原生图文 / 视频

· 层结构：64 层，16 组「3 × (Gated DeltaNet → FFN) + 1 × (Gated Attention → FFN)」——48 层线性注意力，16 层全注意力

· 隐藏层：5120；FFN 中间维 17408

· 上下文：原生 262,144 token，YaRN 可扩到 1,000,000

· MTP：权重内已训练多步 Multi-Token Prediction 头，不用另下草稿模型

· 思考：默认开；reasoning_effort 可调 xhigh / medium / low；preserve_thinking 默认保留历史思考块

这套架构对部署有一个直接影响：它采用混合 GDN，大部分层走线性注意力，每隔三层插入一层全注意力。长上下文场景下，KV 缓存会比纯 Transformer 更省，但服务端还要为 GDN 状态池预留显存。并发上不去时，问题未必出在模型权重，也可能是这部分状态占用了余量，第三节会回到这个参数。

权重三档

模型 量化 权重
Qwen3.8-27B BF16 Qwen/Qwen3.8-27B
Qwen3.8-27B-FP8 FP8（blockwise） Qwen/Qwen3.8-27B-FP8
Qwen3.8-27B-NVFP4 NVFP4 W4A4 + FP8 projections RadixArk/Qwen3.8-27B-NVFP4

FP8 权重大约 28.5GB，本文以 H100 / H800 / H200 作为示例采用这一档（表中高亮）。NVFP4 约 16.5GB，更适合支持 FP4 Tensor Core 的硬件；具体选择仍要以显卡架构和后端支持情况为准。

03｜如何部署：以 H 系列为例

SGLang cookbook 给出了 H200、RTX PRO 6000、RTX 5090 和 DGX Spark 等硬件的单卡路径。下面先讲通用的部署思路，再以我们使用的 H 系列（Hopper SM90：H100 / H800 / H200）为例给出一套可直接参考的命令；其中文档明确验证的是 H200。H100 / H800 同属 SM90、显存为 80GB，FP8 权重大约 28.5GB，单卡加载后还要为 KV 缓存、GDN 状态和 MTP 校验预留空间。

MTP 不需要另挂草稿模型，checkpoint 中已经包含训练好的多步 MTP 头。SGLang 通过 --speculative-algorithm EAGLE 开启（NEXTN 是同一算法的别名）。本文沿用 cookbook 的推荐组合：3 / 1 / 4，即 3 步、topk 1、草稿 4 个 token。不同 GPU 或后端可能需要调整显存比例、prefill 分块和量化格式，但 MTP 与解析器的配置思路是一致的。

官方部署参考：SGLang Cookbook · Qwen3.8-27B

部署前先分清三件事

MTP 和 DSpark 是两条路径。MTP 使用权重自带的头；DSpark 需要另挂 RadixArk/Qwen3.8-27B-DSpark，两者不要写进同一条命令。

量化格式要和硬件匹配。本文的 H 系列示例使用 FP8；如果显卡没有 FP4 Tensor Core，就不要直接照搬 NVFP4，否则 MLP 可能回退到 Marlin W4A16。

两个解析器都要带上。--reasoning-parser qwen3 和 --tool-call-parser qwen3_coder 少一个，工具调用就可能退化为普通文本，而不是结构化的 tool_calls。

1. 拉镜像、下权重

镜像使用 lmsysorg/sglang:qwen38-27b，权重从 ModelScope 下载 FP8 版本。

docker pull lmsysorg/sglang:qwen38-27b # 按你的盘符改本地目录 modelscope download \ --model Qwen/Qwen3.8-27B-FP8 \ --local_dir /modelshare_readonly/Qwen/Qwen3.8-27B-FP8

2. 单卡启动，打开 MTP

下面按 cookbook 的 H200 配置作为示例基线：FlashInfer、32K prefill chunk、mem-fraction 0.85，再叠加 MTP 3/1/4。H100 / H800 同样是 SM90，命令主体无需调整；其他 GPU 可以沿用启动流程，但要根据显存容量和后端支持情况重新选择量化、prefill 分块与显存比例。多卡机器可用 CUDA_VISIBLE_DEVICES 指定一张卡，27B FP8 不需要 TP。

docker run --gpus '"device=0"' \ --network host \ --name Qwen3.8-27B \ --shm-size=32g --ipc=host -d \ --privileged \ -v /modelshare_readonly/Qwen/Qwen3.8-27B-FP8:/model \ lmsysorg/sglang:qwen38-27b \ python3 -m sglang.launch_server \ --trust-remote-code \ --model-path /model \ --served-model-name Qwen3.8-27B \ --mem-fraction-static 0.85 \ --attention-backend flashinfer \ --chunked-prefill-size 32768 \ --max-prefill-tokens 32768 \ --reasoning-parser qwen3 \ --tool-call-parser qwen3_coder \ --speculative-algorithm EAGLE \ --speculative-num-steps 3 \ --speculative-eagle-topk 1 \ --speculative-num-draft-tokens 4 \ --host 0.0.0.0 \ --port 30000

启动参数的四个关注点

MTP 四件套：EAGLE + steps 3 + topk 1 + draft 4，这是 cookbook 推荐的权重内 MTP 工作点。

prefill chunk：本文的 H 系列示例使用 32K；其他硬件应以对应 cookbook 配置为准，不要机械照搬这一数值。

served-model-name：客户端填写 Qwen3.8-27B，不要填宿主机目录名。

上下文长度：默认 262K。显存较紧或并发要求较高时，可先加 --context-length 65536 或 131072。扩到 1M 需要用 YaRN 覆盖 rope_parameters，并设置 SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1，日常部署不必开启。

3. 启动后确认服务链路

curl http://127.0.0.1:30000/v1/models curl http://127.0.0.1:30000/v1/chat/completions \ -H "Content-Type: application/json" \ -d '{"model":"Qwen3.8-27B","messages":[{"role":"user","content":"用三句话介绍你自己。"}]}'

进程启动只是第一步。还需要确认中文输出和流式响应是否正常，reasoning_content 能否与答案分开，tool_calls 是否保持结构化；再发送一张图片，确认视觉塔已经接入。观察日志中的 max_running_requests 和 MTP 接受率，如果并发受到显存限制，再考虑调整 --mamba-full-memory-ratio。

先用官方采样参数作为基线

· 思考模式：temperature=1.0，top_p=0.95，top_k=20

· 非思考：temperature=0.7，top_p=0.80，top_k=20，presence_penalty=1.5，关掉 enable_thinking

· 长任务不建议一开始就把 reasoning_effort 调到 low。单轮响应可能变快，但分析不足会带来额外重试，总耗时反而可能上升。

04｜怎么测：用 EvalScope 做压力测试

服务启动后，不能只用一轮 curl 判断性能。更实际的做法是逐步提高并发和请求数，观察首 token 延迟、生成吞吐、成功率以及显存变化。这里使用 EvalScope 的 perf 命令做压力测试，官方快速开始文档见：EvalScope Stress Test Quick Start。

下面这组参数将并发梯度设为 1、10、50、100、200，请求数设为 10、20、100、200、400；使用随机数据集，并把输入和输出 token 长度固定为 1024，便于横向比较。--url 和 --tokenizer-path 需要替换成实际服务地址和本地 tokenizer 路径。

evalscope perf \ --parallel 1 10 50 100 200 \ --number 10 20 100 200 400 \ --model qwen3.8-27b \ --url http://repo:30000/v1/chat/completions \ --api openai \ --dataset random \ --max-tokens 1024 \ --min-tokens 1024 \ --prefix-length 0 \ --min-prompt-length 1024 \ --max-prompt-length 1024 \ --tokenizer-path /root/evalscope-test/tokenizer/ \ --extra-args '{"ignore_eos": true}'

06｜结论：先看任务，再决定是否上线

对准备自建服务的团队，Qwen3.8-27B 的判断其实很具体：它把视觉输入、长上下文和 Agent 任务能力放进了单卡可承载的稠密模型。相比需要集群的 2.4T Max，它更接近多数团队可以实际评估和维护的容量档位。

从模型卡数据看，它相对 3.6-27B 的提升主要集中在改代码、操作终端、办公长任务，以及看图和理解界面。SWE-bench Pro 为 61.7，OSWorld 为 84.3，部分编码项超过了更大或闭源的对手。但这些仍是厂商公布的结果，独立复现尚不充分；是否适合生产环境，最终要由自己的仓库、工具链和并发规模决定。

部署示例以 H 系列为基线，选择 FP8，并打开权重内置的 MTP（EAGLE 3/1/4），同时配置 qwen3 和 qwen3_coder 两个解析器。无论使用哪种 GPU，MTP 与 DSpark 都不要混用；量化格式也要先确认硬件是否支持。如果并发受到限制，再回到 GDN 状态池和 --mamba-full-memory-ratio 排查。

这套服务也已接入 NanZi 开源智能体平台，Qwen3.8-27B 可以直接选择。平台入口适合用来验证模型与工具、技能之间的协作效果；仓库地址为 RandyChen1985/nanzi-ai-agent-platform。

最后留三点判断

· 如果需要单卡承载视觉、长上下文和 Agent 任务，27B 是更现实的起点；Max 则是集群级方案。

· 量化方案要和硬件匹配；本文以 H 系列 FP8 部署为例，MTP 和两个解析器属于同一条运行链路。

· 上线前仍要按自己的任务和并发规模复测，NanZi 可以作为一个现成的验证入口。

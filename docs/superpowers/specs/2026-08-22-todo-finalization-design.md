# Todo 清单成功收尾兜底设计

## 背景

当前 `todo_write` 由 Main 通用智能体通过模型调用维护。模型可以在任务开始时创建清单、在执行过程中更新步骤，但任务结束时如果直接生成最终答案而没有再次调用 `todo_write`，前端会保留 `pending` 或 `in_progress` 状态。

## 目标

- 保留模型对过程状态的细粒度控制。
- 确保本轮任务正常成功结束时，Todo 清单不会停留在未完成状态。
- 异常、取消、等待用户确认或等待外部执行时，不把未完成步骤误标为完成。
- 前端最终展示与后端持久化使用同一份收尾后的清单状态。

## 非目标

- 不把 Todo 改造成持久化任务管理系统。
- 不改变单步问答和简单查询的 Todo 触发规则。
- 不要求后端理解每一项任务的业务语义。
- 不新增失败、取消等 Todo 状态；本次继续使用 `pending`、`in_progress`、`completed`。

## 方案

### 状态职责

模型负责：

1. 首次调用 `todo_write` 创建完整任务清单。
2. 工具或子代理阶段完成后更新对应项目。
3. 根据真实执行结果，将已完成的项目标记为 `completed`。

后端负责：

1. 每次接收 `todo_update` 时继续按全量快照更新当前轮次状态。
2. 本轮最终 `execution_status == "success"` 且存在 Todo 清单时，对剩余 `pending` / `in_progress` 项执行成功收尾。
3. 将收尾后的快照同时送入实时事件流和最终时间线持久化。
4. 任务因权限确认或外部执行挂起时，将最近 Todo 快照随运行时挂起状态保存；恢复后先还原该快照再继续收尾。

### 成功收尾规则

- 只处理当前轮次创建的 Todo 清单，不读取或修改其他会话的清单。
- 如果清单已经全部 `completed`，不重复发送更新。
- 如果存在未完成项，将这些项目改为 `completed`，保持内容和顺序不变。
- 兜底事件应在最终成功状态和 assistant 最终答案发送/持久化前产生，确保实时 UI 与历史记录一致。

### 非成功状态规则

以下状态不自动完成：

- `error`
- `cancelled`
- `awaiting_permission`
- `awaiting_external_execution`
- `awaiting_user`

这些状态继续保留模型最后一次提交的 Todo 快照，避免把未执行的步骤伪装成已完成。

## 数据流

```text
模型调用 todo_write
        ↓
当前轮 process_timeline 保存全量 Todo 快照
        ↓
任务执行结束
        ├─ success → 后端补全未完成项 → 发出最终 todo_update → 持久化
        └─ 其他状态 → 保留原快照 → 持久化/等待恢复
```

## 失败处理

- Todo 事件发送失败不能让主任务失败；沿用现有辅助 UI 事件的容错策略。
- 收尾只修改内存中的当前轮快照；如果快照格式异常，则跳过收尾并记录警告。
- 收尾逻辑不得影响 token 统计、最终答案内容、工具执行结果或会话摘要。

## 测试要求

- 成功任务存在未完成 Todo 时，最终快照全部为 `completed`，并产生一次最终更新事件。
- 成功任务已全部完成时，不产生重复收尾事件。
- 错误、取消、等待确认和等待外部执行时，未完成状态保持不变。
- 没有 Todo 的普通任务不产生任何 Todo 事件。
- 前端收到最终更新后展示全部完成状态，历史时间线与实时状态一致。
- 保留现有 `todo_write` 入参校验、全量替换和清单清空行为。

# 个人技能审核发布到平台公共技能库

**日期:** 2026-08-04  
**状态:** 已确认方案，待实现

## 目标

为个人技能增加一条可审计的发布链路：用户保留个人技能并继续自己使用，主动提交当前内容给管理员审核；管理员通过后，平台生成独立的公共技能发布版本，供全平台运行时和 Agent 公共 Skills 白名单使用。

核心不变量：

1. 个人目录始终是用户自己的可编辑源，不因提交或发布而被移动、删除或改成平台目录。
2. 平台目录只承载审核通过的不可变快照；个人后续编辑不会直接影响线上公共技能。
3. 每次重新提交都产生新的候选版本；在新版本通过前，平台继续使用上一版。
4. 个人技能 ID 与平台技能 ID 分离，避免现有运行时“个人同 ID 覆盖全局技能”的合并行为造成歧义。
5. 发布、驳回、下架和重新提交均有状态和审计信息，不依赖目录文件内容推断审核结果。

## 当前实现约束

- 个人技能位于当前用户的 `agent_workspaces/{user_key}/skills/{skill_id}`，通过 `/api/portal/skills/personal` 管理。
- 平台技能位于 `settings.SKILLS_DIR/{skill_id}`，通过 `/api/portal/skills` 管理。
- 运行时会合并平台技能与当前用户个人技能；`list_skill_metas()` 当前按技能 ID 合并且个人技能优先。
- Agent 版本的 `skills_custom=true` 保存的是公共技能 ID 白名单，个人技能不进入该白名单。
- 平台技能现有写权限为 `menu:skills_management`。第一期复用该权限作为审核和平台发布权限，避免新增权限迁移和角色配置范围扩大。

## 方案选择

### 方案 A：提交时直接复制到平台目录

实现最简单，但没有待审核记录、版本快照和回滚边界；管理员只能在复制后人工检查，无法可靠恢复上一版本。不采用。

### 方案 B：个人目录与平台目录共享同一物理文件

无需复制内容，但个人编辑会直接改变全平台行为，个人删除或权限变化也可能破坏公共技能。不采用。

### 方案 C：提交快照、管理员审核、通过后物化平台版本（推荐）

提交时保存个人技能的完整快照和校验信息；审核通过后将该快照安全地物化到平台技能目录。个人源与平台发布版本解耦，适合现有物理目录运行时，也为后续版本、回滚和审计保留边界。

## 用户可见行为

### 个人侧

个人技能卡片显示以下发布状态：

- 未发布：显示“提交为平台技能”。
- 审核中：显示提交时间和当前审核版本，不允许重复提交同一内容。
- 已发布：显示“平台版 vN”，支持“提交新版本”和“查看平台版”。
- 已驳回：显示管理员意见，支持修改后重新提交。

个人技能始终可以继续编辑和自己挂载。编辑已发布个人技能后，状态显示为“平台版 vN 有新的个人修改”，平台仍保持 vN，用户可主动提交新版本。

### 管理员侧

技能工作台增加“发布审核”入口，复用 `menu:skills_management` 权限。审核详情至少展示：

- 技能名称、描述、个人技能 ID、拟发布的平台技能名称；
- 提交人、提交时间、当前候选版本；
- `SKILL.md` 预览和完整文件树；
- 文件数量、总大小、内容哈希以及基础安全校验结果；
- 若存在上一平台版本，展示本次候选与当前线上版本的差异摘要。

管理员可以“通过并发布”或“驳回并填写原因”。平台已有版本在新版本审核期间保持启用。

### 发布后的两个对象

展示名称允许相同，但系统内部不是两个同 ID 技能：

```text
我的技能：用户日志分析       personal_skill_id = user-log-analysis
平台技能：用户日志分析 v1     platform_skill_id = public-user-log-analysis-xxxx
```

个人卡片显示来源和平台版本关联，平台卡片显示“来源：个人技能提交”。同一用户可以继续使用个人版，也可以显式挂载平台版；发布不自动替换当前会话中的个人技能。

## 数据模型

新增两张平台主数据库表，并同步 MySQL `db-prod` 与 PostgreSQL `db-prod-pg` 初始化/迁移脚本。

### `skill_publications`

代表一条平台技能发布谱系。

- `id`：UUID，发布谱系主键；
- `platform_skill_id`：稳定的平台运行时 ID，全局唯一；
- `source_user_id`：原个人技能所有者；
- `source_personal_skill_id`：原个人技能 ID；
- `name`、`description`：当前平台展示元数据；
- `current_version`：当前已发布版本号；
- `status`：`PENDING`、`PUBLISHED` 或 `REVOKED`；首次提交到首次通过之间为 `PENDING`；
- `created_at`、`updated_at`、`revoked_at`、`revoked_by`。

### `skill_publication_versions`

代表一次提交和审核结果。

- `id`：版本记录主键；
- `publication_id`：所属发布谱系；
- `version_number`：从 1 开始递增；
- `status`：`PENDING`、`APPROVED`、`REJECTED`、`SUPERSEDED`；
- `snapshot_path`：提交快照的受控存储路径；
- `content_sha256`、`file_count`、`total_size`：快照指纹；
- `submitted_by`、`submitted_at`；
- `reviewed_by`、`reviewed_at`、`review_comment`；
- `published_at`、`materialized_path`。

同一发布谱系最多一个 `PENDING` 版本。批准新版本时，旧的 `APPROVED` 版本变为 `SUPERSEDED`，但保留记录和快照，以支持回滚或审计。

## API 与数据流

### 个人提交

`POST /api/portal/skills/personal/{skill_id}/publication-requests`

只要求登录，服务端必须重新解析当前用户个人目录，不能接受客户端任意路径。处理步骤：

1. 校验个人技能归属、`SKILL.md` 存在、路径安全和快照大小限制；
2. 对文件树做基础校验，拒绝隐藏敏感文件、符号链接、越界路径和超限文件；
3. 将整个技能目录复制为只读候选快照，生成哈希和文件统计；
4. 创建或复用 `skill_publications`，写入新的 `PENDING` 版本；
5. 返回发布谱系、候选版本和状态。

### 查看个人发布状态

个人技能列表和详情附带：`publication_id`、`publication_status`、`current_public_version`、`pending_version`、`last_review_comment`。个人只能查看和操作自己的发布记录。

### 管理员审核

审核接口统一挂在 `/api/portal/skills/publication-requests`，并放在 `/api/portal/skills/{skill_id}` 动态路由之前，避免路由误匹配：

- `GET /api/portal/skills/publication-requests`：待审核列表；
- `GET /api/portal/skills/publication-requests/{version_id}`：审核详情和快照预览；
- `POST /api/portal/skills/publication-requests/{version_id}/approve`：通过并发布；
- `POST /api/portal/skills/publication-requests/{version_id}/reject`：驳回并保存原因。

所有接口使用 `menu:skills_management`。审核操作需要校验版本仍为 `PENDING`，防止重复审批覆盖后续结果。

### 通过并发布

批准操作在数据库事务和受控文件操作之间保持明确状态：

1. 读取候选快照并再次执行安全校验；
2. 首次通过时生成稳定的 `platform_skill_id`；后续版本沿用该 ID；
3. 将快照物化到平台技能目录的临时目录，确认 `SKILL.md` 和文件哈希完整后原子替换活动目录；
4. 将活动平台技能标记为启用，并更新 `current_version`；
5. 将候选版本标为 `APPROVED`，前一活动版本标为 `SUPERSEDED`；
6. 任一文件物化失败时不更新活动目录，数据库记录保持 `PENDING`/可重试状态，不得出现“数据库已发布但目录为空”；若活动目录替换后数据库提交失败，服务必须使用备份目录恢复上一活动版本，并记录失败审计日志。

平台目录中的 `SKILL.md` 必须携带平台技能 ID、发布版本和来源谱系的非敏感元数据，但不能写入个人工作区路径或凭据内容。

### 驳回和下架

- 驳回只改变候选版本状态，个人源文件不变；
- 下架只禁用平台发布谱系并保留已发布快照，个人技能仍可使用；
- 个人删除源技能不删除已经审核通过的平台技能；平台记录保留原提交人和来源 ID，来源文件不可用时标记为“源技能已删除”。

## 运行时边界

- 平台运行时只扫描 `SKILLS_DIR` 中已物化且启用的 `platform_skill_id`；
- 个人运行时仍扫描当前用户个人目录；
- Agent 的 `skills_custom` 只允许选择平台技能 ID，不暴露个人 ID；
- 所有挂载元数据继续携带 `scope`，平台版为 `global`，个人版为 `personal`；
- 不在首期改变“个人技能自动匹配优先”的现有行为；同名技能由用户通过作用域标签和显式挂载区分。

## 错误处理与安全

- 快照生成失败不创建 `PENDING` 记录，个人源保持不变；
- 审核期间个人源发生变化不修改已提交快照，页面提示“个人技能已有新修改”；
- 重复提交相同哈希时返回已有待审核版本，不创建重复任务；
- 同一发布谱系不允许并行待审核版本；
- 所有文件操作复用现有路径穿越、压缩包和大小限制逻辑，并增加符号链接和敏感文件阻断；
- 日志记录提交、审核、发布、驳回、下架的操作者和对象 ID，不记录 `SKILL.md` 全文或凭据内容。

## 验收与测试

后端覆盖：

1. 用户只能提交自己的个人技能；
2. 合法技能能够生成完整快照，个人目录仍存在；
3. 快照与提交后个人修改隔离；
4. 非 `menu:skills_management` 用户不能查看或处理审核队列；
5. 通过后平台目录生成独立 ID，个人和平台同名不发生 ID 覆盖；
6. 驳回保存原因且个人技能可重新提交；
7. v2 审核期间平台继续运行 v1，通过后才切换；
8. 平台下架和个人删除互不误删；
9. 重复审批、路径穿越、符号链接、隐藏敏感文件和超限快照均被阻断；
10. MySQL/PostgreSQL 迁移脚本结构一致。

前端契约覆盖：

- 个人技能卡片的发布状态和版本信息；
- 提交确认、审核中、驳回原因和重新提交入口；
- 管理员审核列表、详情、通过/驳回操作；
- 个人版与平台版同名时的作用域、版本和来源标识；
- 审核失败时不清空编辑器或改变当前挂载。

第一期验证以针对性后端测试、前端契约测试、迁移静态检查和 `git diff --check` 为主；不把未连接真实数据库、真实登录浏览器或部署环境的测试表述为完整发布验收。

## 明确不做

- 不做个人技能自动替换为平台技能；
- 不做公开市场评分、收藏、评论或租户外分享；
- 不允许个人直接修改平台已发布文件；
- 不首期引入复杂的多人会签和灰度流量；
- 不把个人目录直接挂载为平台目录。

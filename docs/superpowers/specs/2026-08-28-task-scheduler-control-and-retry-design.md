# 任务调度器节点开关与失败重试设计

## 背景

当前 FastAPI 进程启动时都会初始化进程内的 APScheduler。多节点部署时，所有节点都会加载同一批任务；智能体任务有 Redis 执行锁保护，但报告订阅等调度任务没有统一的跨节点排他控制。因此本次先提供明确的运维开关，并把智能体定时任务的已有重试能力暴露到编辑页面。

## 方案

### 调度器节点开关

- 新增环境变量 `TASK_SCHEDULER_ENABLED`，类型为布尔值，默认 `true`，保持单节点部署的现有行为。
- `true` 时启动当前节点的 APScheduler；`false` 时不启动任何调度任务，包括智能体定时任务、报告订阅和系统维护/同步任务。
- 关闭节点仍正常提供 API，不影响手动执行任务。
- 开启节点每 30 秒从共享任务库对账一次，因此关闭节点上的新增、修改、停用和删除会最终同步到开启节点；无需让关闭节点启动调度器。
- 该开关是人工运维约束，不是自动 leader election。多节点部署时应明确只让一个节点（建议独立 scheduler 实例）设置为 `true`，其他 API 节点设置为 `false`；滚动发布期间需避免两个节点同时为 `true`。

### 智能体任务失败重试

- 复用现有任务配置字段：`config.max_retries` 和 `config.retry_delay_seconds`。
- 编辑入口为“任务中心 → 编辑定时任务 → 执行失败策略”。
- 最大重试次数支持 `0–3` 次，默认 `0`（不重试）；重试间隔页面以分钟填写，允许 `1–60` 分钟，保存时转换为秒。
- 仅对 Cron/interval 等定时触发失败生效；“立即执行”不自动重试。
- Redis 锁冲突属于跳过，不视为失败重试；报告订阅本次不新增自动重试，避免扩大改动范围。

## 不在本次范围

- 不实现数据库租约、自动选主或 scheduler 分片。
- 不改变现有任务表结构和迁移。
- 不给报告订阅增加自动重试配置。

## 验证边界

- 自动验证配置解析、启动分支源码契约、编辑页读写契约及现有相关测试。
- 不由开发代理运行服务、部署脚本或真实多节点验收；真实部署需由用户在控制台验证单节点启用、API 节点禁用和滚动发布行为。

# 嵌入个人中心「返回对话」浮标的方向感知收起

- 日期：2026-10-16
- 涉及：`frontend/src/views/EmbedPersonal.vue`、`tests/frontend/test_embed_personal_contract.py`

## 背景

对话页头部的「我的账号」会跳转到 `/embed/personal`。该页刻意不带 Dashboard 导航
（设计约定「只出现个人中心本身」），而小程序 web-view 里小程序的返回键是**退出整个
web-view**、不回退站内路由，所以此前补了一个「返回对话」浮标。

浮标经过数轮实测修正后定稿为：`fixed` 定位、右下角、仅移动端（`sm:hidden`）、
`min-h-11`（44px）触控热区、`bg-white/90` 无边框 + `shadow-sm` 分隔。

## 问题

用户提出：「现在浮标是固定在右下角的吗，能不能可以拖动位置呢」。

追问后确认**核心痛点是遮挡**：浮标是 `fixed` 在视口上的浮层，滚动正文时必然压住内容。

评估「可拖动」后认为它不是对症解法：拖拽只是把遮挡**换一个位置**，且要额外处理
拖动/滚动冲突、拖动/点击冲突，以及小程序 web-view 下 `localStorage` 可能受限导致
位置记忆失效。故提出三个方案供选择。

## 方案对比

| 方案 | 做法 | 评价 |
|---|---|---|
| 1. 滚动时自动淡出 | 滚动中隐藏，停止约 400ms 后恢复 | 可预测，不需要用户学习新交互 |
| **2. 方向感知（选中）** | 向下滚收起，向上滚立即出现 | 贴合意图：向上滚通常意味着想回上面 |
| 3. 拖拽 + 位置记忆 | `touchstart/move/end` + `localStorage` | 未解决遮挡本身，且有三处额外冲突要处理 |

用户选择**方案 2**。

### 采纳方案 2 时补上的兜底

纯方向感知有一个洞：**滚到底部后才想返回时，最后一段动作是向下滚，浮标恰好是收起的**。

因此增加一条兜底：**停止滚动约 1.2 秒后自动恢复**。这样既保留「向上滚即时响应」
（比方案 1 的「停下才回来」更快），又不会出现「滚到底找不到返回键」。

## 设计

### 行为

| 触发 | 浮标状态 |
|---|---|
| 向下滚动（看内容） | 收起：`opacity-0` + 下移 2px + 不可点 |
| 向上滚动（想回上面） | **立即**恢复，并取消待执行的恢复定时器 |
| 停止滚动 1.2 秒 | 自动恢复（兜底） |
| 位移 < 8px | 忽略（见下） |
| `scrollTop ≤ 64px`（顶部附近） | 不收起（见下） |

### 实现要点

- **滚动容器不是 `window`**。个人中心的滚动容器是
  `<div class="h-full w-full overflow-y-auto">`，监听**必须挂在容器上**；
  挂到 `window` 会一个事件都收不到。
- 状态：一个 `backFabHidden` ref、一个恢复定时器、一个上次 `scrollTop`。
- **抖动阈值 8px**：移动端惯性滚动会产生大量微小反向抖动，不设阈值浮标会疯狂闪烁。
- **顶部附近不收起（`scrollTop ≤ 64px`）**：否则用户刚进入页面、只向下滚一点点，
  返回键就立刻消失了——「在看内容」的语义还不成立。64px 约等于一个头部高度。
- **向上滚要清掉恢复定时器**：否则「向上滚立即恢复」之后，先前排队的兜底定时器
  还会再触发一次。虽无副作用，但属于多余的状态跳变。
- 收起态样式：`opacity-0 pointer-events-none translate-y-2`，`transition-all` 约 200ms。
- 清理：`onUnmounted` 移除监听并 `clearTimeout`。

### 无障碍

收起时必须同时加 `aria-hidden="true"`。否则屏幕阅读器仍会读到一个「看不见但存在」
的返回按钮——`pointer-events-none` 只挡住指针，挡不住辅助技术。

## 测试计划

沿用 `tests/frontend` 既有的源码静态断言风格（`pytest.mark.no_infrastructure`），
新增断言：

- 滚动监听挂在**容器 ref** 上，而不是 `window`
- 向上滚 → 立即恢复，且取消待执行的恢复定时器
- 停止滚动 → **兜底恢复**
- 存在位移阈值
- 顶部附近（`scrollTop ≤ 64px`）不收起
- 收起态含 `pointer-events-none` 与 `aria-hidden`
- `onUnmounted` 中清理监听与定时器
- `sm:hidden` 仍然保留

每条新断言都要做**变异验证**（故意破坏实现，确认测试确实失败），避免出现
「测试通过但方向是错的」——本项目此前已出现过一次此类问题：某条断言把
「必须看不清」固化成了契约，变异验证全绿却与目标相反。

## 明确不做（YAGNI）

- ~~不做拖拽与位置记忆（用户已选择方向感知）~~ → **见下方「后续修订」，拖拽已追加**
- 不做位置持久化
- 不引入任何手势库

## 后续修订（2026-10-16 同日追加）

用户在看到实机效果后补充（原文，附截图）：「还是需要能支持拖动，但是不需要持久化记忆，
因为有时候会挡住我后面的按钮，我要手动拖开」——截图里浮标正好压住「访问凭证（API KEY）」
卡片下方的「查看」按钮。

**本节推翻了上面 YAGNI 里的「不做拖拽」**，理由成立：滚动收起解决的是**滚动时**的遮挡，
而拖动解决的是**静止时**浮标恰巧压住某个控件——两者正交，不互相替代。

### 追加的设计决策

| 决策 | 做法 | 理由 |
|---|---|---|
| 定位 | 未拖动时仍 `bottom-4 right-4`；拖动过就改用绝对坐标 `left`/`top` | 手指跟手，且不必从默认位置反推 |
| 拖动 vs 滚动 | 位移 < 8px 不接管手势，越过阈值才 `preventDefault` | 否则轻滑就变拖动，页面也滚不动 |
| 拖动 vs 点击 | 拖完 300ms 内抑制返回点击 | 否则「拖开」会顺手把用户送回对话页 |
| 拖动 vs 边界 | 夹在视口内（含 8px 留白） | 否则能拖出屏幕、再也点不到 |
| 持久化 | **不写任何存储** | 用户的明确要求 |
| 过渡 | `transition-all` → `transition-opacity` | 位置变化不走动画，拖动才跟手 |

### 追加的测试

`test_embed_personal_contract.py` 由 18 项增至 **24 项**。其中
`test_drag_position_is_not_persisted` 是**反向断言**（断言不存在存储写入），
实现前天然通过——它的有效性由变异验证单独证明（把位置写进 `localStorage` 后精确失败）。

另一条 `test_dragged_position_switches_to_absolute_coordinates` 首版写得过弱：
只断言「标签里含 `fabPos`」，而 `:class` 里也有 `fabPos`，导致删掉 `:style` 后仍然全绿。
已改为断言落在 `:style` 与 `left`/`top` 上。

### 仍未验证

真机 web-view 内 `touchmove` 的 `preventDefault` 能否真正阻止宿主页面滚动
（部分 WebView 对 `passive` 默认值有别）；拖动后浮标是否会被底部安全区或键盘弹出顶掉位置。

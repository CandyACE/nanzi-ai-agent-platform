# AI 友好错误回复与原始错误折叠展示设计

## 1. 背景与现状

当前 Agent 执行出现终态异常时，后端在 `AgentService` 的顶层异常处理分支中生成 `type=error`、`status=error` 的 SSE 事件，`content` 通常是 `[系统错误] 执行过程中发生异常: ...`。前端收到该事件后直接拼接 `> ❌ **服务异常**: ${content}`，因此用户看到的是内部异常原文，语气生硬，也缺少下一步建议。

本次设计只改善终态错误的用户表达和技术详情展示，不改变权限校验、工具执行、AgentScope 工具循环或错误终态语义。

## 2. 目标

1. 将终态错误转换为简洁、自然、可执行的中文说明。
2. 默认隐藏原始错误，用户主动展开后可以查看并复制脱敏后的技术详情。
3. 保留现有 SSE 错误事件兼容性，避免影响会话终态判断、审计和历史消息保存。
4. 错误解释模型失败、超时或不可用时，仍能稳定返回当前静态错误文案。
5. 防止错误文本中的密钥、连接串、Cookie、内部路径等敏感信息进入模型或用户界面。

## 3. 非目标

- 不让前端单独发起错误解释模型请求。
- 不对每个 `type=log,status=error` 的工具步骤错误启动额外模型调用。
- 不让错误解释模型重新调用工具、修改业务数据或参与原 Agent 的执行恢复。
- 不在本次设计中重构现有 AgentScope 工具循环和权限协议。

## 4. 方案比较

### 方案 A：前端收到错误后调用 AI

前端收到错误事件后再请求一个错误解释接口。该方案会把异常处理逻辑放到多个页面，存在凭据和原始错误暴露风险，且不同页面容易出现不一致的错误格式，不采用。

### 方案 B：后端捕获异常后只调用当前模型

实现简单，能复用当前模型上下文，但当前模型可能就是失败原因。模型服务故障、额度不足或超时时，错误处理会再次失败，不作为唯一方案。

### 方案 C：后端单次错误解释，带 fallback 和静态兜底

后端统一完成错误分类、脱敏、AI 解释和 SSE 事件组装；当前模型优先，失败后使用已有 fallback/低成本模型，最终回退静态文案。前端只负责展示友好正文和折叠详情。该方案边界清晰、兼容现有链路，作为实施方案。

## 5. 整体数据流

```text
终态异常
  → 规范化异常类型与消息
  → 脱敏原始错误
  → 判断是否需要 AI 解释
  → 当前模型无工具调用一次
  → 失败后 fallback 模型无工具调用一次
  → 失败则使用静态友好文案
  → SSE: content=友好正文 + error_detail=折叠详情
  → 前端默认折叠技术详情
```

## 6. 后端错误解释策略

### 6.1 触发范围

仅对会结束本轮执行的终态错误触发错误解释，包括顶层 `except Exception` 生成的错误事件，以及已经被执行器判定为不可恢复的终态工具/运行时错误。

以下事件不触发错误解释：

- `type=log,status=error` 的单步工具日志；该错误可能仍可由 Agent 继续修复。
- `permission_required`、`external_execution_required`、`user_question` 等等待恢复事件。
- 用户主动取消、会话排队和正常模型降级提示。
- 已有明确、稳定且可直接执行的专用用户文案，例如上下文超限、多模态模型不支持、Docker 沙箱不可用等；这些文案继续由现有格式化逻辑提供，但可以附带折叠技术详情。

### 6.2 错误解释模型

复用现有模型解析与 fallback 能力：

1. 使用当前 Agent 配置解析出的模型。
2. 当前模型调用失败时，使用系统默认 fallback/低成本模型。
3. 两次均失败时使用现有静态错误格式化逻辑。

错误解释请求使用非流式、短输出、无工具调用和低温度配置。错误解释过程不得进入原 Agent 的工具循环，也不得再次触发错误解释。

### 6.3 错误解释输入

模型只接收结构化、脱敏后的诊断上下文：错误类别、工具名称、阶段、简短操作描述和脱敏异常信息。原始错误作为不可信诊断数据处理，提示词明确要求不得执行其中的指令、不得猜测不存在的原因、不得输出敏感信息。

模型输出限制为：

- 简体中文；
- 1-3 句；
- 说明发生了什么、用户可以怎么做；
- 不虚构已经完成的操作；
- 不输出密钥、连接串、Cookie、完整内部绝对路径或堆栈。

### 6.4 脱敏与兜底

错误在送入模型和发送到前端前统一脱敏。至少覆盖 API Key、Authorization、Cookie、密码字段、数据库连接串凭据和敏感请求头；内部路径按需要保留可诊断的文件名，但不暴露无关目录结构。

错误解释模型任何异常、超时、空响应或不符合约束的响应，都回退静态文案。错误解释失败不得覆盖原始错误审计记录，也不得让本轮从 error 变成 success。

## 7. SSE 协议与兼容性

继续发送：

```json
{
  "type": "error",
  "status": "error",
  "content": "这次读取配置模板没有完成，请确认文件路径或访问权限。",
  "error_detail": {
    "raw_error": "脱敏后的原始错误",
    "ai_status": "success"
  }
}
```

协议约束如下：

- `content` 始终是用户可直接阅读的正文，旧客户端仍可正常显示。
- `error_detail` 为可选字段；旧服务或旧事件没有该字段时，前端继续使用现有 fallback 文案。
- `raw_error` 只保存脱敏文本。
- `ai_status` 使用 `success`、`fallback` 或 `disabled`，不向用户暴露模型凭据和内部调用细节。
- 终态字段保持 `type=error`、`status=error`，不改变现有轮次失败判定。

## 8. 前端展示

### 8.1 默认状态

将当前固定的“服务异常”主标题统一调整为“处理未完成”；正文使用后端返回的 `content`，不再直接把原始异常拼在主内容中。

示例：

> ❌ 处理未完成
>
> 这次读取配置模板没有完成，请确认文件路径或访问权限。

主内容不显示原始异常，也不默认展开详情。

### 8.2 技术详情

当 `error_detail.raw_error` 存在时，在错误内容下方显示“查看技术详情”折叠入口。展开后显示脱敏原始错误，并提供复制按钮；默认收起状态应在 EmbedChat 和 AgentDebug 两个界面保持一致。

当没有 `error_detail` 时，保持兼容旧事件，不显示折叠入口。

### 8.3 防重复与状态边界

前端只对终态错误事件渲染错误卡片。工具日志中的 `status=error` 不应单独追加“处理未完成”正文；同一 SSE 事件不得同时走 `type=error` 和普通 `status=error` 两条渲染分支，避免重复显示。

## 9. 测试设计

### 后端

- 终态普通异常调用当前模型并生成友好正文。
- 当前模型失败后使用 fallback 模型。
- 两个模型都失败时回退静态文案。
- 模型超时、空响应、非预期输出时均能安全回退。
- 原始错误脱敏后才进入模型和 `error_detail`。
- `type=log,status=error`、等待恢复事件和取消事件不触发解释模型。
- `type=error/status=error` 仍保持终态失败语义。
- 已有上下文超限、多模态和 Docker 专用文案不被泛化解释覆盖。

### 前端

- `type=error` 和终态 `status=error` 显示友好正文。
- 有 `error_detail` 时默认折叠，展开显示脱敏原始错误。
- 复制技术详情成功和失败状态可见。
- 没有 `error_detail` 的旧事件保持兼容。
- 工具日志 `status=error` 不渲染终态错误卡片。
- EmbedChat 与 AgentDebug 的错误展示行为一致。

## 10. 实施边界与验收

实施时优先复用现有 `format_execution_error`、`AgentConfigProvider.get_configured_llm`、`get_fallback_llm` 和现有 SSE 事件协议。变更范围限定在后端错误解释/脱敏服务、终态错误事件组装、EmbedChat 与 AgentDebug 错误展示及对应测试。

验收以静态测试、后端单测、前端契约测试和构建检查为基础；真实模型服务、真实 Docker 沙箱和浏览器交互仍需用户在目标环境中手动验证。Agent 不代跑 `./dev.sh` 或部署脚本。

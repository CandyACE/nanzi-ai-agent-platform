# 业务数据确认卡设计

## 目标

为 AI 驱动的业务录入/变更场景提供**通用、可编辑**的「业务数据确认」能力：模型先调用平台通用工具展示待确认字段，用户在聊天内编辑并点击确定/取消后，系统以**普通用户消息**回传固定指令与字段快照，由模型自行理解并决定是否调用 MCP/写入工具。

本期解决的是「字段对不对」，**不**替代现有工具执行确认（`permission_required` / 允许·拒绝）。

## 已确认的产品决策

- 确认类型：业务数据确认，不是工具执行确认。
- 裁决方式：后端不独立做批准状态机；完全由模型理解回传消息后自行触发工具调用。
- 出卡方式：模型调用平台通用工具 `request_user_confirmation`（方案 B），而非解析自由 Markdown。
- 回传内容：固定指令 + **当前字段快照**（确定时为编辑后的值）。
- 字段交互：卡片内可编辑；模型可为单字段设置只读。
- 与 HITL 关系：业务确认 → 用户确定发消息 → 模型调写入工具 →（可选）现有工具允许/拒绝卡仍可出现。
- 一期不做：后端 resume/批准 API、点按钮直接调 MCP、复杂字段控件、后端硬拦未确认写入。

## 用户流程

1. 用户提出录入/变更类需求（如新增供应商）。
2. 模型调用 `request_user_confirmation`，传入标题、字段列表、可选说明与风险提示。
3. 工具返回 `awaiting_user`；前端在对应助手消息下渲染可编辑确认卡。
4. 用户编辑字段后点击「确定」或「取消」。
5. 前端发送一条普通用户消息（固定前缀 + `confirmation_id` + 字段快照）。
6. 模型根据消息继续：确定则按快照调用写入工具；取消则停止写入并可选追问。

```text
用户提出录入需求
    ↓
模型调用 request_user_confirmation（只展示，不写库）
    ↓
工具返回结构化确认载荷
    ↓
前端渲染可编辑确认卡（确定 / 取消）
    ↓
用户点击 → 发送普通用户消息（固定指令 + 当前字段快照）
    ↓
模型理解消息 → 自行调用 MCP/写入工具（可再走工具执行确认）
```

## 架构

### 边界

| 做 | 不做 |
|---|---|
| 通用确认工具 + 通用前端卡 | 后端批准状态机 / resume API |
| 点按钮 = 发用户消息 | 点按钮直接调 MCP |
| 与 `permission_required` 并存 | 替代或混用工具执行确认 |
| 提示词约束「确认前不写入」 | 一期用后端硬拦写入 |

### 后端

- 新增平台内置工具 `request_user_confirmation`。
- `permission_scope=read`，避免再弹工具执行确认卡。
- 工具只校验入参并返回结构化结果（含 `confirmation_id`、`status=awaiting_user`、以及供前端使用的 UI 载荷）；不写业务库、不挂起 AgentScope permission 流。
- 不新增独立确认/resume HTTP API；回传走现有聊天发消息入口。

### 前端

- 新增共享组件（如 `BusinessConfirmationCard`），在 EmbedChat / AgentDebug 复用。
- 识别 `request_user_confirmation` 的工具调用/结果，将 `title/fields/...` 写入消息上的 `businessConfirmation` 状态。
- 状态：`pending`（可编辑可点）→ `submitted`（只读、按钮禁用）；同会话新卡出现时旧卡可标为 `stale`。
- **不**调用 `/api/v1/chat/permissions/{id}/confirm`。

### 与现有能力区分

| 能力 | 用途 |
|---|---|
| 业务确认卡（本设计） | 字段对不对 |
| 工具执行确认卡 | MCP/工具要不要执行 |
| `quick:` 按钮 | 澄清/导航快捷指令，不承担业务确认 |

## 工具契约

### 名称

`request_user_confirmation`

### 入参

```json
{
  "title": "请确认供应商信息",
  "summary": "确认后我将为您录入 ITAM 系统。",
  "fields": [
    {
      "key": "supplier_name",
      "label": "供应商名称",
      "value": "北京神马科技有限公司",
      "editable": true,
      "value_type": "string"
    }
  ],
  "confirm_label": "确定",
  "cancel_label": "取消",
  "risk_note": "可选风险提示"
}
```

约定：

- `fields[].key`：稳定标识，回传与展示均使用。
- `value_type`：一期支持 `string | number | boolean | text`；更复杂结构先序列化为 `string`。
- `editable`：默认 `true`；可对个别字段设 `false`。
- `confirm_label` / `cancel_label`：可选，缺省为「确定」「取消」。

### 出参（模型可见）

```json
{
  "status": "awaiting_user",
  "confirmation_id": "bc_xxx",
  "message": "已向用户展示确认卡，请等待用户确定或取消后再继续。",
  "ui": {
    "title": "请确认供应商信息",
    "summary": "...",
    "fields": [],
    "confirm_label": "确定",
    "cancel_label": "取消",
    "risk_note": "..."
  }
}
```

入参非法时返回明确错误，前端不出卡；模型应补全后重试。

## 回传用户消息格式

点击后发送**普通用户消息**（非独立 API）。

### 确定

```text
【业务确认】用户已确定
confirmation_id: bc_xxx
请根据以下已确认字段继续执行（如需写入请调用相应工具）：
- 供应商名称 (supplier_name): 北京神马科技有限公司
- ...
```

### 取消

```text
【业务确认】用户已取消
confirmation_id: bc_xxx
请停止本次录入/变更，不要调用写入类工具。如需修改请询问用户。
（附带卡片当时字段快照，便于模型对照）
```

原则：

- 固定前缀 `【业务确认】`，便于提示词与模型识别。
- 始终携带当前字段快照；确定使用编辑后的值。
- `confirmation_id` 便于多轮对照，不做服务端会话锁定。

## 前端确认卡

### 布局

标题 → 可编辑字段表（标签 | 控件）→ 可选 `summary` / `risk_note` → 确定 / 取消。

### 状态机（纯前端）

```text
pending -> submitted
pending -> stale   # 可选：同会话更新确认卡时
```

- 点一次即锁定，防止重复发送。
- 确定前用卡片当前编辑值组装快照。
- 历史回放：已提交可只读展示；未提交且已失效显示为失效。一期可不做服务端持久化确认状态，以发出的用户消息为准。

### 弱校验（一期）

必填为空时可警告，仍允许提交；强校验留二期。

## 提示词与挂载

### 提示词（工具 description + 系统提示/Skill）

1. 涉及录入 / 修改 / 删除业务数据前，必须先调用 `request_user_confirmation`。
2. 工具返回 `awaiting_user` 后停止，等待用户下一条消息。
3. 收到 `【业务确认】用户已确定`：按快照字段继续，需要时再调写入工具。
4. 收到 `【业务确认】用户已取消`：不调用写入类工具，可追问如何修改。
5. 禁止在未确认时声称「已录入成功」。

### 挂载策略

| 智能体类型 | 是否挂载 |
|---|---|
| 有写入类 MCP / 业务录入能力 | 默认挂载 |
| 纯问答 / 只读检索 | 不挂 |
| 任务中心定时任务 | 默认不走交互确认（无可点 UI）；或任务配置显式关闭 |

## 错误与边界

- Schema 不合法：工具报错，不出卡。
- 连点：`submitted` 后禁用按钮。
- 多张确认卡：仅最新一张可操作；旧卡 `stale`。
- 模型跳过确认直接写入：一期靠提示词；真正执行时仍可走工具 HITL。
- 与工具执行确认顺序固定为：业务确认 → 用户消息 → 模型调 MCP →（可选）工具允许/拒绝。

## 测试覆盖

- 工具入参/出参契约测试。
- 前端：渲染、编辑、确定/取消消息正文、`submitted` 锁定、与 `permission_required` 同屏不互相覆盖。
- 可选：挂载与提示词契约测试。
- 更新 `tests/CHECKLIST.md` 中对应自动化清单（实现阶段执行）。

## 明确不做（一期）

- 后端批准状态机 / `data_confirmation_required` resume API。
- 用确认结果直接调用 MCP。
- 替代工具执行确认。
- 日期选择器、多选标签等复杂控件（一期用文本/数字/布尔）。
- 后端强制拦截「未业务确认不得写入」。

## 实现分期建议

1. **P0**：工具注册 + 契约；前端确认卡 + 回传消息；基础提示词；EmbedChat/AgentDebug 接入。
2. **P1**：挂载策略（写入类智能体默认挂）、历史只读回放、`stale` 处理、CHECKLIST/文档。
3. **P2**：可配置必填强校验、更丰富 `value_type`、可选「确认前禁止写入」的软策略增强。

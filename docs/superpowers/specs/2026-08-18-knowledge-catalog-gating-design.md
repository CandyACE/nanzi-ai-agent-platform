# 知识库目录门控与一次性检索兜底设计

## 背景

当前 `_KNOWLEDGE_SIGNALS` 只要命中“政策”等通用词，再叠加“查询/查看”等动作词，就可能把问题直接路由为知识库请求。这样会把没有对应授权知识库的公开信息问题交给知识库子代理，产生无效调用，并在检索不可用时返回误导性的“内部资料不可用”。

提示词中的知识库摘要可能被截断，而 `list_accessible_knowledge_bases` 能返回完整目录；两者如果各自维护范围或判定逻辑，也会造成模型看到的范围与实际检索范围不一致。

## 目标

1. 将 `_KNOWLEDGE_SIGNALS` 降级为“可能需要知识库”的候选信号，不能单独触发知识库子代理。
2. 使用当前用户实际可访问的完整知识库目录，结合名称、描述、标签、备注做泛化相关性判断，不写领域词白名单。
3. 目录与当前问题有高置信语义匹配时，才允许正常知识库路由，并将匹配知识库限制在有效权限范围内。
4. 没有高置信匹配但问题仍可能需要内部资料时，最多允许一次直接知识库检索兜底；不得因此强制知识库子代理。
5. 无权限、有效目录为空、目录加载失败分别表达，不能把它们混为“没有匹配”。
6. 用户当前轮次显式指定知识库或附件时，显式范围优先于目录匹配。

## 非目标

- 不增加“航班/机票/航空”等领域词硬编码。
- 不让模型在每次请求前调用完整目录工具；目录应由服务端在已有权限上下文中读取，列表工具继续作为显式能力使用。
- 不改变知识库工具本身的权限校验，目录门控只是路由优化，工具权限仍是最终边界。

## 方案

建立一个共享的授权目录读取层，返回完整的知识库元数据和状态：`available`、`empty`、`unavailable`。提示词摘要、路由门控和 `list_accessible_knowledge_bases` 都从该层取得同一权限范围；提示词仍只注入有界摘要，服务端路由使用完整结构化目录。

路由过程采用三段式：

1. 先处理显式知识库选择和明确的非知识库边界。
2. 对目录元数据做通用文本归一化与相关性评分。名称、描述、标签、备注中的多字段命中且具有足够区分度时才视为高置信匹配；候选信号本身不能升级为高置信匹配。
3. 高置信匹配走既有知识库路由；没有高置信匹配时保留一次直接检索兜底许可，但 `should_delegate` 必须为假。检索执行器消费该许可并记录一次性状态，后续不得重复检索或再次唤起知识库子代理。

目录不可用时不伪造“无匹配”：可继续走已有通用/公开信息路径，但只在已有知识库候选且有效权限范围非空时允许一次兜底。有效权限为空时禁止搜索。

## 兼容性与可观测性

- 保留现有 `RequestDecision`/`TurnDecision` 的默认行为，新增字段使用默认值，避免影响非知识库调用方。
- 在路由决策中保留目录状态、匹配 ID 和是否允许兜底，便于日志与测试解释“为什么没有调用子代理”。
- 检索工具继续根据有效 dataset IDs 做最终权限解析；目录匹配结果只能缩小范围，不能扩大范围。

## 回归场景

- “查看某航班的准点率和退改签政策”：不能仅因“政策”进入正常知识库子代理；有有效权限时最多直接检索一次。
- “查内部员工出差报销政策”：若授权目录元数据匹配，则正常知识库路由。
- 授权目录为空或不可用：不产生无权限检索；不可用与无匹配状态可区分。
- 显式指定知识库：即使自然语言与目录文本不重合，仍按显式范围处理。
- 路由器未给出强知识库证据时：不得由工具 nudge 再次强制 `sub_agent_call`。

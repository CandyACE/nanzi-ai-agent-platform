# 自动路由与指定专家执行链统一及延迟优化设计

## 目标

在不改变指定专家现有语义、权限边界、知识库/数据查询安全门禁和最终执行结果的前提下，重构自动路由与指定专家的入口关系：

1. 两种模式都先得到统一的目标专家解析结果，再进入同一条目标专家执行链。
2. 自动路由只保留“选择目标专家”所必需的额外逻辑，避免把完整业务资源加载和多专家编排提前到路由阶段。
3. 通过候选目录缓存、路由上下文瘦身、资源和 ChatBI 资格校验懒加载、快速路径、轻量路由模型和最小路由输出，降低自动路由的首字节延迟和总耗时。
4. 保留可观测性，使优化前后可以明确回答耗时来自候选查询、路由模型、权限校验、资源目录还是数据资格判断。

## 非目标

- 不把目标专家选择注册成模型可调用的内置工具。工具调用发生在目标专家已经选定、Prompt 和工具清单已经建立之后，会增加一次模型/工具往返，并且时机过晚。
- 不改变指定专家的直接选择语义。用户明确指定的 `agent_id`、`agent_name` 或 `version_id` 仍然优先于自动路由。
- 不取消最终目标专家的权限校验、能力校验、数据/知识库安全门禁或执行前工具预检。
- 不默认开启多专家协作。除非满足现有明确的复合任务条件，否则自动路由只选择一个主专家。
- 本设计阶段不直接修改运行代码，也不启动服务、不操作生产数据库、不自动提交 Git。

## 当前执行路径与问题

当前入口在 `ContextManager` 中已经区分了两类目标选择：

- 指定专家：根据 `version_id > agent_id > agent_name` 解析目标配置，然后进入目标专家执行链。
- 自动路由：先加载可见专家和用户授权范围，执行若干启发式判断；无法直接决定时调用路由模型，得到 `agent_id/agent_name` 以及语义证据，再加载目标配置。

目标配置确定后，两类请求大部分流程一致：

1. 最终解析并校验目标专家权限。
2. 创建或恢复上下文，加载记忆、画像、资源目录、主专家/子专家信息。
3. 组装 Prompt 和工具清单。
4. 经过 Dispatcher 判断知识、数据或通用执行分支。
5. 进入 Assistant/Knowledge/Data runner、工具循环、流式输出和持久化。

自动路由额外耗时主要来自目标选择之前的工作：候选专家元数据和授权过滤、知识库授权目录、路由上下文构建、路由模型调用及重试、语义证据解析、ChatBI 数据集资格判断，以及不必要的 secondary agent 生成。当前 `route_elapsed_ms` 主要是聚合值，不能定位这些子阶段。

## 新的总体结构

```text
请求
  │
  ├─ 显式身份存在 ───────────────┐
  │                              │
  └─ 无显式身份 → AutoRouter ────┤  仅负责解析目标专家
                                 ▼
                    AgentTargetResolution
                                 │
                    load + permission + capability
                                 │
                    共享目标专家执行链
                                 │
            context → prompt/tools → dispatcher → runner → SSE/persist
```

### 统一目标解析契约

新增一个服务端内部的数据契约，名称可采用 `ResolvedAgentTarget` 或 `AgentTargetResolution`，放在路由/上下文管理的公共模型位置，字段建议如下：

```python
class AgentTargetResolution:
    agent_id: int
    agent_name: str | None
    version_id: int | None
    provenance: Literal[
        "direct_agent_selection",
        "auto_route",
        "metadata_dataset_scope",
        "session_affinity",
        "deterministic_fast_path",
    ]
    confidence: float | None
    route_evidence: dict[str, Any] | None
    secondary_agent_ids: list[int] | None
```

约束：

- `agent_id` 是后续加载配置的唯一主键；`agent_name` 只用于显示、日志和兼容已有路由结果。
- `provenance` 只描述目标如何选出，不等同于权限已通过；权限仍由统一的最终校验负责。
- `route_evidence` 默认只保留必要的结构化证据，不携带完整路由 Prompt 或原始内部解释。
- `secondary_agent_ids` 默认为空；只有确实满足复合任务条件时才填充。
- 指定专家构造的结果必须继续使用 `direct_agent_selection`，保证现有 Dispatcher/runner 的直接选择分支行为不变。

## 阶段 1：统一目标解析与共享执行链

### 1.1 保留两个入口，合并一个出口

保留以下两个选择入口：

- `resolve_explicit_target(request)`：处理 `version_id`、`agent_id`、`agent_name`，遵循现有优先级和错误语义。
- `resolve_auto_target(request)`：执行自动路由、候选限制、确定性快速路径和必要的路由模型调用。

两个入口都只返回 `AgentTargetResolution`，不在入口内创建完整 Agent、不组装最终 Prompt、不执行工具、不重复执行 Dispatcher。

然后统一进入：

```text
AgentTargetResolution
  → load_agent_config
  → verify_target_permission
  → verify_target_capability/availability
  → build TurnDecision
  → shared context/prompt/tools/dispatcher/runner pipeline
```

### 1.2 保持现有安全语义

- 显式身份解析失败仍然直接返回原有错误，不静默回退到自动路由。
- 自动路由选出的目标仍然必须经过最终 `PermissionService.check_permission`。
- Dispatcher 仍然根据 `TurnDecision`、目标能力和请求类型决定知识/数据/通用分支。
- Main 专家的数据防幻觉保护、工具预检、工具循环熔断和流式输出逻辑不因统一入口而绕过。
- `metadata_dataset_ids` 的强制数据路由继续保留独立优先级，且不能被普通自动路由覆盖。
- 现有 secondary agent 的启用条件和多专家执行能力先保持兼容；阶段 2 再收紧默认生成策略。

### 1.3 阶段 1 的直接收益边界

这一阶段主要是结构收敛和行为保护，不应承诺显著降低自动路由的模型调用耗时。它能减少重复解析、重复加载和分支漂移，为后续缓存和懒加载提供稳定插入点；真正的延迟下降来自阶段 2、3。

## 阶段 2：缩短自动路由前置逻辑

### 2.1 授权候选专家目录缓存

缓存“当前用户可路由的候选专家摘要”，而不是缓存最终权限结论或完整 Agent 配置。

缓存键至少应包含：

- 用户身份或租户身份；
- 角色/权限版本或等价的权限变更版本号；
- 路由场景所需的候选范围版本；
- 必要的组织、工作区或数据域隔离信息。

缓存值只保存路由所需的紧凑字段，例如 `agent_id`、名称、短描述、能力标签、是否启用和路由优先级。完整 Prompt、工具权限、资源目录和密钥配置不进入路由缓存。

失效策略：

- 专家发布、下线、路由元数据修改时失效相关目录；
- 用户角色或授权关系变更时按权限版本失效；
- 没有可靠版本号时使用短 TTL，并保留请求级最终权限校验；
- 缓存异常时回源读取，不改变正确性，只影响性能。

### 2.2 路由 Prompt 瘦身

默认路由上下文只包含：

- 当前用户问题；
- 必要的最近对话摘要或少量最近轮次；
- 候选专家的紧凑名称、短描述和能力标签；
- 必要的场景约束和输出格式。

默认不加载：

- 完整专家 Prompt；
- 全量工具清单；
- 全量资源目录；
- 与本次问题无关的知识库详情；
- 完整历史消息和长篇内部说明。

资源/知识库目录只在问题出现知识库、资源、文件、数据源等明确信号，或确定性判断存在歧义时按需加载。目录仍必须经过授权过滤，且只提供路由所需的最小摘要。

### 2.3 ChatBI 资格校验懒加载

保留当前 ChatBI 资格校验的 fail-closed 语义，但改变执行时机：

- 普通闲聊、问候、非数据问题不触发数据集资格查询；
- 只有目标候选具备数据能力，或路由语义明确要求业务数据时，才调用授权数据集候选解析；
- 如果确定性路径已经得到非数据目标，不再提前做 ChatBI qualification；
- 如果数据资格查询失败，按现有安全策略拒绝、降级或交给原有 fallback，不把未验证的数据能力当成已授权。

### 2.4 多专家默认收敛为单主专家

自动路由的默认结果只生成一个主专家。只有下列条件同时满足时才允许产生 secondary agents：

- 用户明确提出跨领域、串联或并行协作；或现有确定性规则判定为复合任务；
- 主专家不足以独立完成任务；
- 多专家能力已经启用；
- 所有 secondary agent 均通过授权和可用性检查。

这样可以避免路由阶段为普通问题提前构造多专家上下文、Prompt 和调度信息，同时保留既有复合任务能力。

## 阶段 3：快速路径、轻量路由和最小输出

### 3.1 快速路径优先级

在调用路由模型前，按以下顺序尝试低成本判断：

1. 显式专家或版本号：直接解析，不进入自动路由。
2. `metadata_dataset_ids`：沿用强制数据域路径。
3. 明确问候、确认、资源/文件后续操作、网页请求等现有确定性路径。
4. 高置信度的会话专家亲和性：对紧接着的追问复用上一轮目标，但必须满足上下文连续、候选仍可用、权限仍有效、问题未出现新领域切换信号。
5. 单候选专家：保持现有 sole-candidate shortcut，并确保仍做最终权限检查。
6. 轻量路由模型：只对无法安全确定的请求调用。

任何快速路径都必须设置清晰的“不适用”条件；低置信度或领域切换应回到正常自动路由，不能为了省一次模型调用而误选目标。

### 3.2 轻量路由模型配置

路由模型配置与业务回答模型分离，至少支持独立配置：

- `routing_model`；
- 路由模型的上下文上限；
- 路由超时和最多一次重试；
- 路由模型的最大输出 token；
- 失败时的确定性 fallback 策略。

默认优先使用低延迟、结构化输出稳定的模型。路由模型只负责目标选择，不生成面向用户的答案，也不执行业务工具。

### 3.3 最小路由输出

普通路由默认只要求：

```json
{
  "agent_id": 123,
  "confidence": 0.91,
  "provenance": "auto_route"
}
```

兼容期间可以继续接受 `agent_name`，但服务端应尽早归一到 `agent_id`。只有在以下场景才要求扩展语义字段：

- ChatBI/数据问题，需要数据域、时间范围、指标等证据；
- 知识库问题，需要授权知识目录约束；
- 复合任务，需要 secondary agent 判定；
- 低置信度或存在候选冲突，需要可审计的约束信息。

路由结果解析失败时不执行开放式二次追问；先使用有限重试或安全 fallback，避免路由阶段产生不可控的多轮链路。

## 共享逻辑与自动路由特定逻辑

| 阶段 | 指定专家 | 自动路由 | 新方案归属 |
|---|---|---|---|
| 目标来源 | 请求中的 `version_id/agent_id/agent_name` | 候选过滤、快速路径、路由模型 | 两个入口，各自只负责生成统一目标解析结果 |
| 候选专家目录 | 不需要用于选择 | 需要，且可缓存 | 自动路由特定 |
| 路由 Prompt/路由模型 | 不需要 | 仅无法快速确定时需要 | 自动路由特定 |
| 授权目录/资源摘要 | 执行阶段按需加载 | 路由阶段仅在必要时加载最小摘要，执行阶段仍按需加载 | 共享安全能力，加载时机不同 |
| ChatBI 资格 | 目标和请求需要时校验 | 目标/语义确认需要时懒加载 | 共享安全门禁，自动路由延后触发 |
| 目标配置加载 | 需要 | 需要 | 共享 |
| 最终权限校验 | 必须 | 必须 | 共享 |
| `TurnDecision` | 直接选择来源 | 路由来源或元数据来源 | 共享决策模型 |
| Context/Prompt/Tools | 需要 | 需要 | 共享 |
| Dispatcher/Runner/工具循环/SSE | 需要 | 需要 | 共享 |
| secondary agents | 通常无 | 仅复合任务启用 | 共享能力，自动路由默认关闭 |

## 延迟观测与验收指标

在统一解析入口增加分阶段计时，至少包括：

- `route_total_ms`；
- `candidate_catalog_ms`；
- `authorized_agent_catalog_ms`；
- `knowledge_catalog_ms`；
- `resource_catalog_ms`；
- `router_prompt_ms`；
- `router_llm_ms`；
- `router_retry_ms`；
- `dataset_qualification_ms`；
- `target_config_ms`；
- `target_permission_ms`；
- `route_shortcut`、`route_model`、`route_cache_hit`、`route_secondary_count`。

同时记录指定专家的同名共享阶段耗时，用于区分“自动路由选择耗时”和“目标专家执行耗时”。日志中不记录完整用户隐私内容、完整 Prompt 或未授权资源内容。

延迟模型为：

```text
T_direct = T_common
T_auto   = T_route + T_common
```

阶段 1 主要减少重复和分支差异；阶段 2、3 目标是让：

```text
T_route_new ≈ cached candidate lookup
             + deterministic shortcut 或 light router LLM
             + target permission/config gate
             + only-when-needed qualification
```

不能在没有基线数据前承诺固定毫秒数。验收重点是：

- 自动路由的候选目录缓存命中时不再重复完整授权目录查询；
- 普通问题不加载完整资源目录、不触发 ChatBI 资格查询、不生成 secondary agent；
- 可安全确定的请求不调用路由模型；
- 需要模型时只发生一次轻量路由调用，最多一次受控重试；
- 指定专家的共享执行阶段结果和权限行为不回归；
- 自动路由仍不会把未授权专家、知识库或数据集暴露给后续执行。

## 回归与验证策略

### 单元测试

- 显式身份优先级：`version_id > agent_id > agent_name`。
- 显式目标解析失败不回退自动路由。
- 自动路由结果和显式结果均能构造合法 `AgentTargetResolution` 与 `TurnDecision`。
- 候选目录缓存命中、过期、权限版本变化、专家发布失效和回源失败。
- 路由 Prompt 只包含允许的紧凑字段；资源目录和完整工具清单按需加载。
- 非数据请求不触发 ChatBI qualification；数据请求仍 fail-closed。
- 默认 `secondary_agent_ids` 为空，复合任务才允许填充。
- 路由模型最小 JSON、兼容 `agent_name`、解析失败和一次重试。
- session affinity 的连续追问、权限变化、领域切换和低置信度边界。

### 集成/契约测试

- 指定专家和自动路由最终都经过同一套配置加载、权限校验、Dispatcher、runner、工具预检和流式持久化。
- 指定专家的直接选择仍保持 `direct_agent_selection` 行为，特别是数据能力和 Main 防幻觉门禁。
- `metadata_dataset_ids` 仍优先于普通自动路由。
- 知识库请求仍只使用授权知识目录；无权限时不产生越权 fallback。
- 自动路由单主专家和复合任务多专家的执行结果分别验证。

### 性能验证

使用相同用户、相同权限、相同问题和相同模型配置，对指定专家、旧自动路由、新自动路由分别采集：

- 首个路由结果耗时；
- 首 token/首个可见事件耗时；
- 路由总耗时；
- 总响应耗时；
- 路由模型调用次数和重试次数；
- 目录/资格查询次数；
- 缓存命中率。

至少覆盖问候、普通通用问题、数据问题、知识库问题、资源问题、连续追问、领域切换和复合任务。服务启停由用户在控制台完成，Agent 不运行 `./dev.sh`。

## 分阶段发布

1. 先落地统一 `AgentTargetResolution` 和计时字段，保持路由策略不变。
2. 开启候选目录缓存、路由 Prompt 瘦身和 ChatBI 懒加载，保留可配置开关便于回退。
3. 开启快速路径、轻量路由模型和最小输出；默认关闭普通请求的 secondary agent 生成。
4. 对比自动路由与指定专家的共享阶段耗时和错误率，再逐步扩大缓存 TTL、快速路径命中范围和轻量模型流量。

回退原则：任何阶段都可以关闭新增优化开关，回到原有候选读取、完整路由输出或路由模型配置；不回退最终权限校验和数据/知识安全门禁。

## 验收标准

- 自动路由和指定专家在目标确定后进入同一条共享执行链，代码中不再维护两套完整执行流程。
- 自动路由额外逻辑被限制在统一目标解析阶段，且每个额外子阶段都有独立计时。
- 普通自动路由请求不会无条件加载完整资源/知识目录、查询 ChatBI 资格或生成 secondary agent。
- 安全快速路径可以跳过路由模型；无法安全判断时仍回到受控路由模型。
- 轻量路由输出不会丢失数据、知识库和复合任务所需的安全证据。
- 指定专家的权限、数据、知识库、工具和流式行为回归测试通过。
- 性能测试能证明延迟下降来自具体阶段，而不是仅因测试样本或模型响应波动。

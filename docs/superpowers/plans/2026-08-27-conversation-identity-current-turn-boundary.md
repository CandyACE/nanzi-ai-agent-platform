# 会话身份与当前轮边界修复计划

## 目标

修复以下两类问题：

1. 会话历史、资源范围、压缩记录和数据库回退必须严格按 `user_id + conversation_id` 隔离；缺少可靠用户身份时直接失败，禁止降级为 `anonymous`。
2. 执行器必须明确区分本次前端实时输入与历史上下文。历史中的 ChatBI 查询、旧工具摘要或旧任务不能独立触发当前轮工具；是否使用工具只能由当前轮输入及其合法追问关系决定。

## 实施步骤

### 1. 建立身份归一化与 fail-closed 测试

- 增加统一的用户身份解析函数：优先使用认证上下文中的稳定 `user_id`，必要时使用认证系统提供的稳定 `id`；空值、空白值和 `anonymous` 均视为缺失。
- 为缺失身份、不同用户相同会话 ID、合法身份归一化补充单元测试。
- 先运行这些测试，确认当前实现会暴露 anonymous 降级或错误归属问题。

### 2. 收紧会话相关存储键

- 修改 `MemoryService`、`ConversationResourceService`、上下文压缩日志等会话相关 key builder，禁止生成 `anonymous` 会话键。
- 保留管理员明确传入的用户范围能力，但不允许普通请求用空身份进入历史读取、写入、删除或资源访问路径。
- 补充 Redis key、资源范围和压缩日志的隔离测试。

### 3. 修复历史读取与审计回退归属

- 在聊天入口和相关历史管理接口统一要求可靠用户身份。
- Redis 为空时，数据库 fallback 同时约束 `conversation_id` 与 `AgentExecutionHistory.user_id`；不再以管理员身份、username 猜测或单独 conversation ID 返回普通用户历史。
- 审计写入使用同一套身份归一化规则，避免新记录继续产生无法归属的历史。
- 补充 API/服务测试：同会话 ID 的跨用户隔离、缺身份拒绝、当前用户可回退读取。

### 4. 固化“当前轮输入”与“历史背景”结构

- 在 Assistant 执行器入口显式接收当前轮用户输入，不再只依靠“消息列表最后一条 user”作为隐式约定。
- 将历史消息转换成不可执行的历史背景块，将本次输入作为唯一当前轮用户消息传给模型；保留必要的工具摘要和附件信息，但不把历史 user/assistant 角色继续伪装成当前轮对话。
- 补充转换测试：历史中含 ChatBI 查询、工具摘要或旧任务时，当前输入仍被单独标记；历史不会成为当前工具触发源。

### 5. 工具暴露与当前轮调度（经评审废弃动态裁剪门禁）

- **评审结论**：前期探索的方案 C（在执行器前用死板规则动态裁剪工具集合）经实测发现会导致严重的“过度防御”——当用户进行多轮纠错追问（如“你仔细看看，你有这个工具了”）时，门禁会把本该拥有的委派、记忆与业务工具误杀，严重破坏大模型自主工具调用能力。
- **最终落地设计**：废除动态裁剪门禁，保持工具全量真实暴露（`内置隐式工具 + 智能体配置工具 + 挂载的 MCP 工具`）。
- 历史不会成为当前工具触发源的核心保障由“历史工具记录纯文本化/无执行凭据”以及“大模型自主根据当前轮语义理解决策”承担，不再由硬编码规则在中间乱砍工具。

### 6. 回归验证与审查

- 运行身份、历史转换、工具门禁和 Assistant 执行链的聚焦 pytest。
- 运行相关前端契约测试、Python 编译检查和 scoped `git diff --check`。
- 检查工作区，保留用户已有的 Excel 无关修改，不启动 `./dev.sh` 或部署脚本。
- 完成代码自审；若当前环境提供独立代码审查能力，再提交审查，否则明确列出未做的真实服务/浏览器验收。

## 验收标准

- 不同用户即使使用相同 `conversation_id`，也不能互读、互删或互写历史。
- 缺少用户身份时不会生成或访问 `anonymous` 会话范围。
- 当前输入为普通对话时，历史 ChatBI/系统负载任务不会启动工具循环。
- 当前输入明确要求工具能力时，匹配的工具仍可用，且不影响既有权限与确认机制。
- 当前输入与历史任务无关时，模型收到的上下文能明确区分历史背景和本轮请求。
